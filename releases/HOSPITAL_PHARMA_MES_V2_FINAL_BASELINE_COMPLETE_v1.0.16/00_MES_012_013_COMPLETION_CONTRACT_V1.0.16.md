Existing ReleaseDecision table is the sole quality decision source, distinguished by release_scope. ## 2. Quality-plan producer and freeze

An approved qms_production_plan belongs to exactly one MainBatch. It specifies a FINISHED material identity, one approved qc_specification_version_id for that material, and nonempty balanceRules. It may be authored/edited only while MainBatch is DRAFT. Draft → APPROVED requires an independent approver, signature and current usable material/specification evidence; approval freezes exact specification/item snapshots and plan digest. Subsequent ordinary edits are prohibited. Existing historic/legacy batches without plans can retain dispatch/execution behavior but completion/finished QA must fail closed; no plan or PASS evidence is backfilled.

Production dispatch consumes the actual approved plan, when present, and includes its identity/digest/content in the existing immutable ProcessSnapshot. BatchReleased initializes mes_balance_rule rows from that snapshot in the same transaction; no new definition source. An approved plan is mandatory for material-balance completion and finished-product QA. Rule creation does not mutate a published process package or previously released batch. A failed dispatch rolls back rules/instances/eBR/snapshot together.

QualityPlan fields: mainBatchId, finishedMaterialId, qcSpecificationVersionId, balanceRules[]. Each rule has balanceCode, basis(BATCH/OPERATION/PACKAGING), operationCode(nullable, required for OPERATION), materialId(nullable filter), unitId, formulaExpr, toleranceLow, toleranceHigh and checkPoint(OPERATION_COMPLETE/BATCH_COMPLETE/QA_RELEASE). Unique balanceCode within plan; valid unit, finite decimal bounds with low<=high; at least one BATCH_COMPLETE rule. Operation codes must exist in the dispatched route. For an event subset spanning different materials, conversion must be a global unit conversion; no material-specific conversion may be applied to a mixed-material sum. Missing conversion, dimensional mismatch or lossy rounding is an error, never an ignored event.

## 3. Quantity facts and safe balance expressions

Reuse mes_quantity_event. CHARGE remains authored atomically by the existing charge producer; ISSUE and RETURN are derived from actual confirmed issue/return facts, not independently supplied totals. The QMS source synchronizer appends an event once per original source identity under the batch root lock; existing source rows remain immutable. Dispatch never counts as consumption. The remaining OUTPUT/SAMPLE/LOSS/SCRAP/WIP observations are controlled append-only production quantity records with operation/lot as applicable, signed operator/time/reason and source_ref; they are not stock adjustments. OUTPUT requires the finished material from the frozen plan and creates/associates a batch-owned internal finished lot initially QUARANTINE/BLOCKED plus physical stock ledger once. WIP records represent measured outstanding quantity; net active WIP is included only when explicitly selected in the rule. A reversal references one actual event, keeps its source/amount/unit identity and appends exact negative amount once; original event, charge, issue and inventory history are never overwritten. Reversing OUTPUT also requires the lot's current decision/stock/consumption constraints and corresponding reversible physical ledger evidence; RELEASED or consumed output cannot be reversed through this action. CHARGE/confirmed logistics reversals belong to their source producer, not generic production-observation reversal.

formulaExpr is JSON with closed schema: {dslVersion:1,expected:Expr,actual:Expr,metric:DIFFERENCE_PCT|YIELD_PCT}. Expr is one of {sum:EventType[]}, {constant:decimalString}, {op:ADD|SUBTRACT|MULTIPLY|DIVIDE,left:Expr,right:Expr}; no executable strings. Allowed event types: CHARGE, ISSUE, RETURN, OUTPUT, SAMPLE, LOSS, SCRAP, WIP. Max64 nodes/depth8; decimal operands are exact finite strings, max24 digits/8 fraction digits. ADD/SUBTRACT require equal dimensional bases; multiplication permits one dimensionless operand; division permits a dimensionless divisor or equal quantity units yielding a dimensionless ratio. Each sum uses the rule's batch/operation/material filter and explicit unit conversion. Apply reversals to their original type; do not also sum REVERSAL as a separate input. Empty source coverage for a referenced event type fails BALANCE_INPUT_MISSING; a real zero observation is permitted for LOSS/SAMPLE/SCRAP/WIP. Divide-by-zero or expected<=0 fails BALANCE_INPUT_INVALID. Computation uses BigDecimal DECIMAL128; stored quantities use decimal(24,8), percent decimal(24,8), HALF_EVEN only at the final persisted metric (input conversion must be exact). expected/actual must both be quantity-valued in rule unit. Difference=actual-expected; differencePct=difference/expected*100; YIELD_PCT=actual/expected*100. Compare unrounded metric inclusively against frozen limits; do not hardcode tolerances or round PASS across a limit.

Recalculation creates a new immutable version per (batch,rule). Persist rule/formula snapshot, exact event ID/amount/unit/source/reversal set and hash, conversion evidence and result values/time. The current result is the latest calculation, not a mutable replacement. A newly appended quantity event changes the input digest and makes a previous result/exception stale. Current gates lock batch and recompute the input digest; rules due at that checkpoint must have latest PASS or exact signed APPROVED_EXCEPTION evidence. No required-rule/plan or stale calculation fails closed. At OPERATION_COMPLETE, select only matching operation-code/checkpoint rules. At BATCH_COMPLETE and QA_RELEASE, all matching rules plus prior operation checkpoints must pass.

Canonical BalanceResult status is PASS or FAIL. Investigation is a separate mutable root OPEN→INVESTIGATING→APPROVED_EXCEPTION|RECALCULATE_REQUIRED, with signed independent approval of one immutable result/input digest. A result never changes FAIL to PASS. The inherited CALCULATED_PASS/CALCULATED_FAIL names describe calculation outcomes, not additional persisted enums; FD shorthand APPROVED refers to investigation approval. Approved exception remains effective only while the exact result and current input digest remain unchanged. Approval requires investigation text, explicit ACCEPT_EXCEPTION or REQUIRE_RECALCULATION, approver distinct from calculator/investigator and valid signature; subsequent calculation cannot silently reuse approval.

## 4. Production Sample, Test and investigation

Use qms_sample with sample_scope=PRODUCTION, main_batch_id and optional material_lot_id belonging to that batch, quantity/unit/source identity and frozen plan/specification. Reuse existing sample states CREATED→COLLECTED→RECEIVED→IN_TEST→TEST_COMPLETED; no duplicate sample table. Production samples never fabricate incoming SamplingTask/InspectionRequest IDs. Existing incoming check/mandatory relationships remain unchanged.

qms_production_test_instance identifies a real production sample and frozen qc_specification_item_id, specification version/hash/snapshot, attempt_no, predecessor instance and approved investigation for a retest. Every required item must have one effective original/approved retest instance. Reuse qms_test_result_revision as sole original-result source, with additive production_test_instance_id; incoming inspection_item_id/test_execution_id are nullable only for the disjoint PRODUCTION branch. An XOR constraint enforces exactly one incoming or production instance. Existing incoming columns/FKs/checks remain effective. Result submission derives PASS/FAIL from frozen numeric limits/text criteria; records original fact, instrument/method/version, signed operator/time and review evidence. INVALID is a signed independent-review disposition of an immutable result, not rewriting its conclusion. Corrections append revision with exact previous ID and reason; valid FAIL cannot become PASS by correction. Approved retest creates a new TestInstance and revision1, consumes its approved quota under root lock and retains original FAIL/OOS.

Production deviation uses existing qms_deviation with investigation_scope=PRODUCTION, main_batch_id, optional matching operation_execution_id, investigation_kind DEVIATION/OOS/OOT, severity MINOR/MAJOR/CRITICAL. OOS references the original production TestResult/TestInstance; FAIL submission opens one scoped OOS idempotently. OOT can be explicitly recorded with original result and documented rationale; no invented trend threshold. The incoming OOS FK/check is extended disjointly to the new production instance, without relaxing incoming requirements.

Deviation states remain OPEN→INVESTIGATING→DECIDED→CLOSED. Edit only OPEN narrative. Investigation requires summary. Signed independent decision uses existing REJECT/AUTHORIZE_RETEST/ACCEPT_WITH_JUSTIFICATION; AUTHORIZE_RETEST specifies bounded positive count (max10), exact original INVALID disposition and reason. Signed closure requires independently reviewed valid original/retest evidence, consumed quota and all linked CAPA complete; no ongoing CRITICAL or unresolved OOS is ignored. CRITICAL blocks operation completion and batch/QA until CLOSED with valid signature. A nonclosed OOS or REJECT decision always blocks QA. A documented noncritical accepted disposition is allowed only after independent signed decision and linked CAPA completion. No deletion or FAIL update.

qms_capa source_type=PRODUCTION_DEVIATION, source_id actual scoped deviation. OPEN→IN_PROGRESS→COMPLETED→VERIFIED; action_text required, completion_text required at completion, signed independent verification with VERIFIED/REOPEN decision. REOPEN returns IN_PROGRESS and preserves verification history. A separate append-only qms_capa_review records every signed verification; VERIFIED requires the latest approved evidence, never only a client flag. New state changes recheck production roots so release cannot race a new/opened critical finding.

It returns exact blockingCodes, evidence digest and allowedActions, never synthetic PASS. QA submission requires PRODUCTION_COMPLETED plus eBR completeness/required independent production review, valid quality plan and current completion gates. Re-read current root/plan/results/reviews/investigations/balance/signature/genealogy/lot evidence under shared locks. Digest mismatch returns409; failed gates422. Registered objectType QA_RELEASE_DECISION allows RELEASE/REJECT only, with exact current version and evidence. Effective decisions form one immutable successor chain per (org,batch,finished lot); unique predecessor prevents competing successors. Incoming decisions are unchanged. New decision, signature, audit, outbox, MainBatch QA_RELEASED/REJECTED and finished lot RELEASED/AVAILABLE or REJECTED/BLOCKED commit together. Superseding decision requires explicit current predecessor, independent QA identity and current gates. A released lot with subsequent physical consumption cannot be retrospectively rejected through normal supersession; controlled investigation/freeze is required.

Generated eBR is an aggregation of original snapshots, current/historical form/field revisions and invalidation lineage, signatures, actual operations/charges/genealogy, QC original/final results, balance calculations/investigations and QA decision. POST ebr/pdf generates a deterministic PDF from that actual model through a maintained Java PDF library, saves immutable existing platform Attachment/file bytes and ebr_pdf_manifest with increasing generation_version, definition_hash, record_digest, file_id/file_hash/generated_by/time. file_id references the existing platform attachment storage, not a new binary store. Exact stored SHA256 must equal downloaded bytes. Final archive is allowed only after a valid finished decision; earlier PENDING_QA print is a marked review copy and cannot satisfy final archive. Repeated exact digest request returns the existing immutable manifest/file; changed authoritative record digest produces a new version and preserves predecessors. Display/read/download permissions are ebr:form:view/qa:batch-review; generation ebr:pdf:generate plus existing attachment permission through delegated business authorization. User-facing PDF includes Unicode Chinese content using a bundled redistributable font with recorded license, all gate evidence and audit/signature identities; no credentials/reauth tokens.

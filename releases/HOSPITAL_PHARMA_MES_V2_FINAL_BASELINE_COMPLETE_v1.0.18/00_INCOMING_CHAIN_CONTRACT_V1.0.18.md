## 1. Shared physical and transaction rules

`M` and `A` are exactly Database Common Column Profiles M and A (BIGINT auto-increment PK, org_id, creator/time; M additionally updater/time/version_no). Every table below has the indicated profile. All columns are NOT NULL unless suffixed `?`. Types: `ID=BIGINT`, `CODE=VARCHAR(80)`, `STATE=VARCHAR(30)`, `TEXT=VARCHAR(1000)`, `QTY=DECIMAL(24,8)`, `TS=DATETIME(3)` UTC, `JSON=LONGTEXT CHECK(JSON_VALID(column))`. Every FK references `id`, uses RESTRICT, and application transactions validate matching organization and parent chain; no cascade deletion. Every business unique/index begins org_id. Mutable header state indexes `(org_id,status,id)` apply to each declared status field; all FKs have `(org_id,fk,id)` lookup indexes. Physical enum CHECK constraints use the dictionaries below. Positive quantities, revision numbers and attempt numbers are CHECKed. Decimal inputs travel as decimal strings to avoid browser float loss.

All writes use platform idempotency and local transaction audit. If-Match is the quoted decimal versionNo of the aggregate root; conflict 409. Header-owned children are inserted under root optimistic lock, incrementing root version once; A rows have no fabricated version. IDs in JSON are strings. Missing/cross-org references return 404 without exposing foreign data; permission 403; business gate 422. No DELETE, generic status setter, duplicate idempotency infrastructure, or free-text replacement for an FK.

record_status tracks document control, never replaces lifecycle status: request DRAFT/SUBMITTED then EFFECTIVE on accept; sampling DRAFT then EFFECTIVE on start and APPROVED on signed completion; inspection task DRAFT then EFFECTIVE on start, SUBMITTED on submit, REVIEWED on review; report mirrors DRAFT/REVIEWED/APPROVED. Sample uses only status. Metadata updates never alter immutable business evidence.

Numeric PASS is server-derived only when value exists and lies within inclusive frozen bounds in the frozen unit; FAIL otherwise. Text PASS requires a populated result and signed analyst assessment against frozen text criteria; no text default PASS. INCONCLUSIVE is inability to determine and blocks passing review/release. INVALID is approved invalidity, distinct from INCONCLUSIVE: supplied only through signed investigation closure disposition, never ordinary result entry/correction. Original stored FAIL remains FAIL; API exposes stored conclusion plus effectiveConclusion INVALID and disposition reference. Raw execution timestamps/actor/instrument and inert JSON evidence cannot be replaced.

Approved retest does not itself invalidate a FAIL. Closure must bind selected_result_revision_id, original_result_disposition VALID/INVALID and reason/signature. INVALID requires demonstrated assignable cause in investigation summary. Release requires selected reviewed PASS, original INVALID disposition and CLOSED investigation; a valid original FAIL remains blocking even if a later retest passes. A generic closed deviation with ACCEPT_WITH_JUSTIFICATION cannot waive a mandatory FAIL or create passing data. For a non-OOS blocking deviation, CLOSED plus accepted signed disposition is required. AUTHORIZE_RETEST permits at most authorized_retest_count new executions (positive), enforced under deviation lock; investigation remains DECIDED until closed, so release remains blocked.

Automatic report generation covers every required source specification item in the request, including multiple tasks/samples. For each item there must be exactly one effective reviewed result: the current revision of its sole reviewed original execution, or the selected result in the sole applicable CLOSED signed investigation resolving that original. Multiple independent original executions or multiple competing selections are ambiguous and return REPORT_RESULT_AMBIGUOUS, never latest timestamp wins. Optional items that were executed are included and must also be reviewed. Missing required/unreviewed/INCONCLUSIVE/INVALID candidates cannot generate an approvable report. Reviewed FAIL may generate a FAIL report for rejection, never a passing release. Generation snapshots exact references/digest only, not a parallel set of numeric results. Report query derives display values through references. A new revision/retargeted investigation/new approved report invalidates stale release evidence and approval digest checks.

## 5. Audit, signature and integration boundaries

Audit each create, named transition, detail/sample generation, execution, result append, review, investigation decision/closure, report, QA/system-rule decision with actor, object, action, reason, request/transaction ID and old/new digests. Business rows preserve reconstructible values, not merely hashes. Result/sample/report references are returned via org-scoped queries. Signatures use existing canonicalizer/provider and single-use reauthentication; no credential payload in audit. Provider types: SAMPLING_PLAN, SAMPLING_TASK, SAMPLE_DISPOSAL, TEST_RESULT_REVISION, INSPECTION_TASK, DEVIATION_DECISION, DEVIATION_CLOSE, INSPECTION_REPORT, MATERIAL_RELEASE_DECISION. Provider registration is mandatory before routes are enabled. Signed commands accept reauthToken, not client-supplied signatureId. After completed-idempotent replay detection, SignatureApplicationService consumes the bound token through ReauthenticationPort on the first attempt before transactional signing. A consumed token is never restored on command failure; retries after failed attempts require fresh reauthentication. SignatureTransactionService then signs the validated transaction-scoped canonical intent under the root lock and persists signature plus business evidence in one transaction; root/version/content gates are rechecked there. No new signature storage/table or prepare endpoint is created. For a new result, signable object ID is server-derived `executionId:nextRevisionNo`, recordVersion is the locked InspectionTask version. For a new release it is `lotId:expectedLotVersion`, recordVersion is the locked MaterialLot version. These signable IDs are strings distinct from the AUTO_INCREMENT business row PK; providers reconstruct committed intent from the immutable signature evidence envelope stored alongside the execution revision or release decision, as specified in §8. For persisted sampling/task/report/deviation/sample objects the signable ID is their existing ID and recordVersion is current root version. Detail/review DTOs return signingTargets with action, objectType, recordId, recordVersion and meaning; client binds /auth/reauth to that exact target and submits the returned token with business fields. For result creation the execution read exposes nextRevisionNo target; corrections use the same immediate-next formula. Deviation decision/close have distinct actions and providers. Generic /records signing must fail without a permitted persisted snapshot or transaction-scoped business-command intent; it must not sign arbitrary client payloads. Business commands enforce token actor/intent/version, canonical digest, independent signer and latest revoked predecessor. Signature/audit/idempotency failure rolls back all domain effects.

Plan signature includes request/item/plan/package count/OTHER name/reason; completion includes plan signature, ordered details/sample IDs/quantities; result includes execution/snapshot/value/conclusion/predecessor; task review includes sorted exact revision IDs; investigation decision includes original FAIL/cause/decision/retest count, closure includes selected result and original disposition; report includes request/spec and ordered original/final/investigation references; release includes lot version/quality/inventory/report digest/effective predecessor/investigation and policy evidence. Signed evidence modifications require a new controlled record/signature; old signatures never silently reused. Fix platform immediate revoked predecessor validation as bounded existing defect, with test.

QMS query interfaces: IncomingQualityQueryService.getLotChain(orgId,lotId) returns receipt→request→sampling detail→sample→task/item→execution and all result revisions→report→release/investigations; InspectionEvidenceQueryService.evaluate(orgId,lotId) returns approved report, original/final references, unresolved investigations and evidenceDigest; MaterialEligibilityService.evaluate(lotId,useContext,at) consumes release and WMS lot/inventory in the final reservation/issue/weigh/charge transaction. Cross-module notifications use MaterialReleased/MaterialRejected events after atomic evidence+lot update; no HTTP envelopes in domain. Real MES-011 charge trace consumes these query contracts; it cannot manufacture mock lot or QC records. Freeze/expiry/retest-date gates remain effective even with historical release.

## 8. Persisted signature envelopes and historical verification

Every signature above persists an immutable evidence envelope in its matching `*_signature_evidence_json` slot in the same transaction as the signature and command. Exact JSON shape: `{objectType: string, objectId: string, recordVersion: integer, canonicalRecord: object, evidenceIds: string[]}`. Values are the server-built, canonicalized signing intent actually passed to the existing signature service, including its original root version and all bound reference/content snapshots. The envelope must be serialized before the root version/state mutation and never regenerated from later mutable header values. It is technical GxP evidence, not independently editable business state or another source of test results. `canonicalRecord` contains the exact signed fields enumerated in §5, including command reason and signature meaning/action as bound by the platform; it never includes reauthentication tokens, passwords or credentials. All evidence IDs are sorted deterministically for canonicalization.

Database constraints pair each nullable signature slot with its JSON evidence slot: `(signature_id IS NULL AND signature_evidence_json IS NULL) OR (signature_id IS NOT NULL AND signature_evidence_json IS NOT NULL)` (substitute the respective plan/completion/disposal/review/decision/close/approval prefixes). TestResultRevision requires both unconditionally. USER_QA ReleaseDecision requires both; SYSTEM_RULE requires both NULL and separate rule evidence. JSON_VALID applies to every nonnull slot. Append-only result/release guards protect their envelopes. Mutable-table guards prohibit update or clearing of a nonnull envelope or paired signature ID: sampling plan and completion, sample disposal, task review, deviation decision and close, report approval. Only the first NULL→value assignment is allowed through the corresponding authorized command; later business transitions may not overwrite that slot. Supersession/correction creates new evidence rather than replacing a slot.

During command signing, the provider uses only the transaction-scoped current intent. During any later signature verification, including generic signature verification after the root version increments, the provider loads the persisted envelope selected by signature ID and reconstructs exactly `{objectType,objectId,recordVersion,canonicalRecord,evidenceIds}`. It verifies the stored envelope against the platform signature digest and original signer/action, never substituting current root status/version or current related records. A mismatch is evidence corruption and fails verification. Current release eligibility additionally checks current business gates; historical cryptographic verification and current eligibility are separate checks.

Detail read DTOs expose `signatureEvidence` entries with slot, signatureId, objectType, objectId and recordVersion. They omit large canonicalRecord payloads by default. `GET /quality/signature-evidence/{signatureId}` returns the exact envelope only after same-org source-object read permission plus `audit:view`; the endpoint cannot edit or sign evidence. It resolves only the incoming record types listed in §5 and returns 404 for absent/foreign records. Platform providers use the same repository resolution internally. Required tests IQ-SIG-05: a result signature verifies after task submit/review version increments; plan signature verifies after sampling completion; decision signature verifies after deviation closure; release signature verifies after lot inventory/quality transitions; unauthorized signature envelope reads fail; changing any envelope byte/reference/version fails digest verification; null-slot mismatch and attempted envelope overwrite fail database guards; SYSTEM_RULE retains null signature/evidence without fabricated signing facts.

Shared `/deviations` API merge rule: overlay operations carry `x-incoming-scope-overlay: true`. The discriminator is `investigationScope`, fixed to `INCOMING_MATERIAL` in every incoming command. Merge with the original production operation using disjoint anyOf branches: incoming typed schema, and a cloned original schema explicitly excluding `investigationScope=INCOMING_MATERIAL`. Preserve original production schemas and behavior; outside this incoming implementation, the unfinished production branch returns DEPENDENCY_NOT_READY. Existing-ID commands resolve the stored target scope before validation; an incoming target requires the incoming typed body and discriminator even if the caller omits/misstates it. Detail reads resolve by stored scope. Incoming lists must explicitly send investigationScope=INCOMING_MATERIAL.

## Production commands and immutable definitions

Orders: DRAFT on create; only DRAFT allows basic editing. First child batch release atomically sets IN_PROGRESS. Lock order while allocating/editing batches; total child planned quantity converted to order unit must not exceed order plan. COMPLETED requires equal allocation and all children PRODUCTION_COMPLETED/PENDING_QA/QA_RELEASED/REJECTED. Rejected quality does not undo production completion. No arbitrary status endpoint.

Batch draft creates no snapshot and no dummy runtime. PUT `/main-batches/{id}` is the approved added operation, uses existing `production:batch:update`, edits draft authored fields only. Sub-batches are authored only before release; retain their independent nullable planned quantity. On release lock order→batch, require usable product/package and matching published eBR version, generate canonical immutable `{process,ebr,materials}` snapshot, create DIRECT execution if no sub-batches or one SUB_BATCH execution per sub-batch, actual operation/runtime records, audit, and commit atomically. Same-org identical snapshot content may reuse hash only after exact content comparison. Include organization in canonical identity to prevent cross-org unique-hash collisions. ProcessSnapshot stores physical source IDs, never guessed line positions.

`ProcessQueryService` currently supplies `requireUsable` and operation IDs, but not formula/route/item/parameter identities. Extend its query result with an immutable identity-bearing view of its actual stored published definition: formulaVersionId, routeVersionId, each formulaItemId, operationDefId and parameterDefId. This is a producer query extension, not a second authored definition. Keep authored source values and identity mapping in the batch snapshot. `EbrQueryService.requirePublished` and `MaterialQueryService.requireUsable` already exist; snapshot the material basic policy (no retired MaterialVersion).

MainBatch follows existing DRAFT→RELEASED→IN_PROGRESS→PRODUCTION_COMPLETED→PENDING_QA states. Here RELEASED is the inherited **production dispatch** enum; it is never a finished-product release decision. QA_RELEASED remains future finished-product authority. Start writes started_at once; production completion writes completed_at once. Required balance/QA dependencies remain fail-closed. Incoming-chain acceptance ends after actual charge and trace; it must not claim finished release or production completion without their real gates.

Operations are created from frozen route, root operations READY and dependent operations PENDING. Completion promotes only successors whose actual predecessors all completed. start READY→IN_PROGRESS; pause IN_PROGRESS→PAUSED; resume PAUSED→IN_PROGRESS; complete IN_PROGRESS→COMPLETED. Failed gates return 422 with no operation/run/value/business-audit mutation, as approved. Successful operation actions drive equipment run intervals: start/resume opens a new segment; pause/complete closes live segments once. Parameter values append only. Gates consume real equipment calibration, applicable qualification, predecessor, material, eBR required-field/rule/review/signature and configured completion evidence. Never map role strings to qualification codes. Clearance-required operations without a real clearance producer remain 422; a client `PASSED` is not evidence. No workflow-runtime dependency.

## WMS reservation and issue contract

Existing routes/permissions stay unchanged; replace stage `DependencyCommand` stubs with concrete DTOs. Reservation requires released/active actual batch and exact frozen formula item/material. `materialLotId` optional means server FEFO selection, never bypass: obtain eligible candidates, order by expiry (known earliest first), then receipt occurrence and ID, lock chosen lots, recheck current release/freeze/expiry/retest and remaining quantity, create one or more ACTIVE reservations. An explicitly selected lot receives identical gates. All quantities use explicit material-specific UOM conversion; unknown conversion/precision loss rejects. Concurrent reservations must not over-allocate.

Issue DRAFT accepts batch, issue number and item lot/formula/quantity. Confirm locks batch/issue/lot, verifies current MaterialEligibilityService and reservation entitlement, and creates dispatch evidence once. Issue is logistical evidence, not actual consumption. `mes_material_charge` alone creates production CONSUME. Do not subtract on-hand twice: any issue movement ledger pair must net zero across locations; no ISSUE negative quantity standing in for CHARGE. Existing issue items do not identify target locations, so current issue confirmation records dispatch/allocation without inventing a destination. Return must not exceed issued-unconsumed quantity after prior returns; preserve original issue and append return evidence. Charged quantity cannot be returned as merely unconsumed issue. Reservation transitions ACTIVE→CONSUMED/RELEASED are controlled internal consequences of actual consumption/return; no generic status API. Partial outstanding entitlement is derived from immutable issued/charge/return evidence under lock, not by rewriting original reserved/issued quantity.

## Weighing, charge and trace

POST `/weighings` submits executionUnitId/materialLotId/formulaItemId/targetQty/actualQty/unitId/scaleEquipmentId/reason. Target must equal the frozen BOM requirement scaled by actual execution plan and exact UOM conversion; target is not client authority. Nullable SubBatch plan cannot be invented from the whole batch: if target basis is unavailable, reject 422 rather than fabricate. Material snapshot supplies weighingRequired, weighingPrecision, weighingTolerancePct and verification policy. Overage is formulation overage, not weighing tolerance. Check `abs(actual-target)/target*100` inclusively against configured tolerance and precision without floating-point rounding. Missing required policy rejects. Scale must be real usable equipment at command time; actor qualification must be valid under an authoritative action mapping. Create commits CONFIRMED only after all gates (DRAFT is pre-confirmation domain state, no new draft API). Verify CONFIRMED→VERIFIED requires independent verifier where required, current version and auditable evidence. Store server actors, not client verifiedBy. Required signature policy uses existing signature platform and digest provider.

Charge requires IN_PROGRESS actual operation of the same execution and batch, exact frozen material/BOM, real incoming eligibility rechecked in the final transaction, positive quantity, usable verified weighing where policy requires, and no prior over-consumption of weighing/issued balance. Lock before reading remaining quantities. Optional weighing is permitted only where frozen material policy permits; it never permits an unmatched BOM material. All locations/containers debited must have sufficient real ledger balance; select and persist the exact consumed segments as ledger evidence. Since existing charge DTO does not select locations, deterministic server consumption uses issued eligible lot stock ordered by location/container ID; no negative bucket is allowed. Same transaction writes Charge + CHARGE QuantityEvent + CONSUME ledger + Genealogy + Audit, or none. `MATERIAL_NOT_ELIGIBLE` is the unified release/quality/inventory/freeze/expiry/retest failure with detailed reason; BOM mismatch remains MATERIAL_NOT_IN_BOM; quantity/tolerance remain CHARGE_QTY_INVALID/WEIGHING_OUT_OF_TOLERANCE.

Existing reverse command retains original charge and appends compensating quantity/ledger/audit evidence before setting REVERSED; never delete genealogy or pretend original use did not occur. It requires permission/reason/current version, prevents repeat reversal and rejects impossible downstream reversal. Stock restoration retains current lot quality/inventory gates; reversal cannot release a frozen lot. Trace shows both original use and reversal status and their audit references.

GET `/trace` accepts mainBatchId or materialLotId (one required). Response is actual graph evidence: MainBatch→ExecutionUnit→Operation→Charge→Weighing→MaterialLot→ReceiptItem→Receipt→delivery attachments and MaterialLot→InspectionRequest→SamplingTask/Detail→Sample→TestExecution→Result revisions→Report→ReleaseDecision/signature, including investigations and superseded facts. Derive incoming graph through incoming query service, never join fake incoming IDs. Both directions must agree on the same charge IDs. No finished-lot creation is necessary to prove incoming-to-production use.

## Immutable signature envelopes

Approved technical GxP evidence completion adds `signature_evidence_json LONGTEXT NOT NULL` to `mes_weighing_record` and `mes_material_charge`, initialized to `[]`. Each applicable successful signed action appends one immutable server-owned envelope `{action, objectType, objectId, recordVersion, canonicalRecord, evidenceIds, signatureId}` in the same business transaction. `recordVersion` is the exact platform signing version, and `canonicalRecord` is the exact canonical JSON payload signed at that action, including the then-current gate/equipment/source evidence. `signatureId` links the existing platform signature; it is appended after signing and is excluded from its own signed canonical payload to avoid a circular digest. No client may submit or amend these fields. Preserve all old envelopes on verification, reversal, re-sign or root-version changes.

During signing the provider returns the transaction-scoped current intent; during later generic verification its existing loadForSignature(org,objectId) method parses the stable action-specific objectId and locates the exact original envelope, checks its linked signature and stored recordVersion, and returns that immutable original canonicalRecord. The objectId includes action and signed version because the platform provider does not receive recordVersion as a lookup argument. An objectId containing only the mutable root ID is forbidden for these action signatures. No new charge signature point is activated; its signature-evidence array remains empty unless an explicitly applicable frozen signing policy already requires a signature on that persisted fact. Never reconstruct an old signature from the mutable current aggregate or its latest gate-evidence array. The envelope is consumed historical evidence, not a second editable business truth. Required tests sign a fact, advance its root version or append a later signed action, verify the earlier signature against its original envelope, reject tampered envelopes, and prove rollback leaves no signature/fact evidence while the already consumed reauthentication token remains unavailable.

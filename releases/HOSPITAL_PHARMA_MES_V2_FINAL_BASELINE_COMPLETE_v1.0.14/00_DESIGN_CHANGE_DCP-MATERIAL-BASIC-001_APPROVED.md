## Authoritative bounded replacement

- Material is an editable basic master: existing identity/descriptive fields, base/pack units, lot control, effective dates, remark, and existing incoming-inspection policy (default true, now on root). New material is ACTIVE; named UPDATE/Disable, with no business versions, submit, approve, or immutable-version edit workflow. Record versionNo remains an internal optimistic-lock token, never a business version in UI. Fixed materialCode cannot be renamed. All edits require authorization, reason, optimistic locking, transactional audit and idempotency.
- Existing material CRUD/disable and supplier-assignment paths remain. Remove /materials/{id}/versions, /submit, /approve and active submit/approve permissions. Closed flat create/update DTOs; no versionId, nested quality/storage/production form, client audit actor or client status. MaterialQuery produces explicit materialId basic snapshots; callers copy the snapshot at use/receipt/batch creation. Subsequent master edits do not change already persisted consumer snapshots. No new receipt/batch business implementation.
- Physical V001–V009 and old baseline releases remain immutable. V010 extends root with requires_incoming_inspection, copying legacy version policy if present, and adds md_material_supplier.preferred. Legacy material version/rule tables and data are retained as retired historical evidence, never written by current application. Existing regulated root states are not mass-rewritten; legacy DRAFT/APPROVED is interpreted as enabled until an explicitly audited maintenance update. Previously required advanced rule columns become nullable; legacy values remain unchanged, with no invented rule defaults or new quality workflow.
- A material can have multiple active (approved=true) supplier relationships. Exactly one is preferred when any active relationship exists; zero when no active relationship exists. Preferred must be an active, currently qualified same-org supplier relationship within inclusive UTC validity. No automatic fallback/promoting suppliers on expiry; use-time eligibility gate remains. Revocation keeps the old row and clears approved/preferred. Assignments lock the material root; root versionNo increments once. Database enforces at most one active preferred per org/material; service enforces exactly one for a nonempty active set. Supplier qualification lifecycle is unchanged.
- Existing material pages become basic create/view/edit with named unit selectors, embedded material-specific unit conversion CRUD, multiple supplier selection and a single preferred radio selection. Query labels stay inline per prior user instruction. Existing routes/permissions for UOM and suppliers are reused; no new menus/routes. No electronic-signature point is removed from process/production/quality.

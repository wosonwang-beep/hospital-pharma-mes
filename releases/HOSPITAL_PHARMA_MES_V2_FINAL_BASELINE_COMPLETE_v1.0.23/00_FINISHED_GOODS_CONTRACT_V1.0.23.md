## 1. Controlled business chain
Production complete → finished inbound request → warehouse confirmation / quarantined stock → finished inspection request → QC acceptance → sampling record / actual production Sample → frozen-standard TestInstance / immutable TestResult → generated inspection report / independent QC approval → batch QA review / signed release → available finished stock → signed shipment / physical stock decrement / source trace.

Production, inbound application, quality processing, QA decision, and logistics states remain separate facets. Do not introduce a single catch-all batch state enum. Existing mother-batch PRODUCTION_COMPLETED/PENDING_QA/QA_RELEASED/REJECTED, lot QUARANTINE/RELEASED/REJECTED, stock BLOCKED/AVAILABLE remain canonical. No generic status update. Batch is the formal finished-product identity; one batch-owned finished lot remains the existing invariant.

## 2. Physical output and warehouse ownership
New signed OUTPUT observations retain actual output quantity, location reference, lot identity, dates and lineage but do not create physical WMS ledger entries. Observation reversal before completion appends the existing signed reversal without stock change when no original stock entry exists. Production completion remains controlled by actual completed operations/eBR/IPC and BATCH_COMPLETE balance. An active approved frozen production plan remains mandatory.

Production creates one inbound request per mother batch after PRODUCTION_COMPLETED. Server derives product, finished lot, base unit, completion time and net signed OUTPUT quantity using exact unit conversions; no client-authored production total. It freezes this source evidence. Warehouse confirmation is separate from request submission and requires an independent warehouse actor, current version, exact unchanged source digest, active actual destination, reason and existing-platform VERIFY signature. Only confirmation appends FINISHED_RECEIPT stock once and records its ledger ID; initial quality/stock QUARANTINE/BLOCKED.

Existing signed output ledgers are immutable historical facts. Explicit legacy confirmation verifies actual positive net output and the existing exact stock quantity/location, links that evidence and does NOT append another receipt quantity. No automatic backfill, fabricated receipt, database reset or physical deletion. Final historical QA decisions remain readable. New release/supersession commands require current extended evidence; already released historical batches are not silently rewritten.

## 3. Inbound request (WMS)
wms_finished_inbound_request uses mutable Profile M, request_no unique(org), main_batch_id unique(org), material_lot_id, product_id, quantity DECIMAL(18,6)>0, unit_id, status DRAFT/SUBMITTED/CONFIRMED/CANCELLED, source_snapshot_json/digest, submitted_by/at, confirmed_by/at, location_id, ledger_id nullable for legacy multi-ledger evidence, signature_id/envelope, reason. FK production batch, lot, product, unit, location, ledger, signature. Request creator cannot warehouse-confirm it. Cancellation only DRAFT/SUBMITTED. Confirmed facts cannot be edited/cancelled. After confirmation frozen stock source evidence and current material lot remain independently traceable.

API / permissions:

All command fields closed; mandatory Idempotency-Key, exact quoted If-Match and integer versionNo for actions. Permission precedes replay; organization verified at every reference.

## 4. Finished inspection and sampling (QMS)
qms_finished_inspection_request Profile M: inspection_request_no unique(org), main_batch_id, material_lot_id, inbound_request_id unique(org), qc_specification_version_id, specification_snapshot_json/digest frozen from the batch's actual approved dispatched plan; status DRAFT/SUBMITTED/ACCEPTED/COMPLETED; requested/submitted/accepted actor/time, reason. It can start only after actual confirmed inbound and production completion. No incoming receipt/supplier identity is fabricated. Submit and QC acceptance are distinct commands.

qms_finished_sampling_record is insert-only using common Profile M base columns (unchanged after insert): inspection_request_id, sample_id unique(org), material_lot_id, sampling_no unique(org), sampling_location, quantity>0, unit_id, sampling_method, sampled_by/at, signature_id/envelope, reason. Sample has existing sample_scope=PRODUCTION, exact main_batch_id AND mandatory finished lot, frozen production plan/specification, sample type TEST_SAMPLE/RETENTION_SAMPLE/RETEST_SAMPLE/OTHER_APPROVED. The sampling action creates the sample and sampling record atomically; cumulative sampled quantity cannot exceed confirmed receipt after exact conversion. Existing production Sample/TestInstance/TestResult/review/OOS/retest ownership is reused. No independent result dataset. Existing incoming sampling relationships remain untouched. Post-completion finished sampling is a dedicated controlled action; it does not relax ordinary production sample creation in IN_PROGRESS.

## Implementation consistency clarifications

An original FAIL remains effective in a report until its own signed closed investigation selects a confirmed authorized retest result; a new unrelated passing sample cannot supersede it. This enforces the approved immutable FAIL/OOS contract. Public request detail/list omit sampling/report collections when their dedicated view permission is absent; complete internal evidence is separate and its digest is independent of the reader. Finished-lot read projection uses existing lot data with nullable supplier batch/receipt/retest fields because finished origin is production, not incoming receiving. No incoming API schema changes.

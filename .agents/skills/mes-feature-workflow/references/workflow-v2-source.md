# MES 功能开发标准工作流 — Skill 创建与工程治理指令 V2.0

## 一、总体目标

使用 `skill-creator` 创建项目级主控 Skill：

`mes-feature-workflow`

将医院制剂 MES 所有新菜单、新功能、新页面、新页面模板和现有功能的重大修改纳入统一的五阶段工作流。

**五阶段固定顺序：**

1. UI UX Pro Max — UI 设计规范与设计稿
2. Product Design — Vue 3 可交互原型与视觉验收
3. 详细设计 — 完善设计文档并冻结开发基线
4. Codex — 复用原型代码并实现真实业务
5. 集成验收 — 功能、接口、权限和 UI 一致性验收

强制要求：

- 不得跳过阶段。
- 不得伪造阶段验收结果。
- 不得将设计图等同于可交互原型。
- 不得将原型构建成功等同于浏览器验收通过。
- 不得将单元测试通过等同于集成验收通过。
- 不得由 Codex 重新设计已经验收的 Vue 页面。
- 未通过上一阶段门禁，不得进入下一阶段。
- 所有流程状态、产物和验收记录必须持久化在项目仓库中。

## 二、启动前检查与现有规范继承

项目根目录优先使用：

`D:\codex\_project\gmp\hospital-pharma-mes`

先确认实际仓库位置、Git 状态、当前基线和现有治理文件。

必须检查：

- `AGENTS.md`
- `MES_TASKS.md`
- `docs/PROJECT_BASELINE.md`
- 当前 FINAL BASELINE
- Global UI Design System
- T1–T6 页面模板规范
- 页面目录与功能详细设计文档
- 现有 API、权限、状态机及数据库设计规范
- 现有 UI 和自动化测试约定

确认 `ui-ux-pro-max-skill`、`skill-creator` 及 Product Design 的实际可用性。

如果工具不存在或无法跨运行环境调用，必须记录阻断原因与标准交接方式。严禁假装已完成插件调用。

现有冻结基线与新规范出现冲突时：

1. 列出冲突项及影响范围。
2. 形成设计变更提案。
3. 经有效批准后更新相应基线。
4. 不得静默覆盖既有规范。

## 三、适用范围与自动触发条件

出现以下任务时必须启动 `mes-feature-workflow`：

- 新增一级、二级或三级菜单
- 新增业务功能模块
- 新增查询、编辑、详情、审核、执行和报表页面
- 新建或修改 T1–T6 页面模板
- 修改已冻结页面的结构、布局和交互
- 修改业务字段、操作权限、业务流程或页面状态
- 新增业务实体、状态机或跨模块业务流程

新增菜单时，不得只创建前端路由。必须同步检查菜单资源、操作权限、后端权限、角色授权、页面入口和测试覆盖。

纯文案修复及不影响冻结契约的低风险问题可以使用简化流程，但必须在任务卡中记录变更范围及允许跳过的检查，不能绕过必要的回归测试。

## 四、第一阶段 — UI UX Pro Max

### 4.1 主要职责

读取现有 UI 设计规范，选择 T1–T6 模板并输出完整页面设计。

不得另起一套与现有系统不一致的视觉规范。

### 4.2 强制 UI 标准

- 整体采用既有 MES 确认的简洁 PC 管理系统风格。
- 顶部导航、左侧菜单、面包屑与全局视觉保持统一。
- 字体、颜色、字号、间距、按钮、卡片、表格和表单使用统一 Design Token。
- 所有字段标签与对应输入控件保持同一行，包括查询条件。
- 查询页必须包含实际查询条件。
- 新增、修改、查看原则上使用独立页面。
- 普通页面仅允许选用已批准的 T1–T6 模板。
- 不得随意展示数据库内部编号、版本号或非业务必要的技术字段。
- 不得自行增加无需求依据的按钮、页签和业务字段。
- 页面须明确 PC 和移动端响应式策略。

菜单权限页面还必须遵循已确认的规则：

- 菜单采用树形结构。
- 菜单名称前的 Checkbox 表示授权可见。
- 菜单对应「只查看」「管理」操作权限。
- 勾选菜单时默认选择管理权限。
- 前后端必须采用一致的授权语义。
- 菜单信息、操作权限和关联角色须按已批准的页面结构展示。

### 4.3 阶段交付物

1. 页面功能与模板映射表。
2. UI 设计稿。
3. 设计标注及 Design Token 引用。
4. 页面布局、字段和按钮说明。
5. 交互行为说明。
6. PC / Mobile 设计约定。
7. 第一阶段审查报告。

### 4.4 G1 门禁

只有满足以下条件才允许通过：

- 已检查现有 UI 基线。
- 已选择合法页面模板。
- 设计稿完整覆盖功能范围。
- 字段、按钮和页面状态有定义。
- 设计审查无未解决的阻断问题。
- 取得有效设计确认记录。

不通过则返回第一阶段修正。

## 五、第二阶段 — Product Design

### 5.1 目标技术栈

必须以以下技术栈作为原型交付契约：

- Vue 3
- TypeScript
- Vite
- Ant Design Vue
- Pinia
- Vue Router

不得以 React 原型或静态 HTML 作为 Vue 源代码交付的替代品。

如果 Product Design 当前执行环境不能直接产出符合要求的 Vue 工程，应当标记为阻断，并使用经批准的 Vue 构建方式，不得谎报框架支持。

### 5.2 原型功能要求

必须实现设计中涉及的主要交互：

- 左侧菜单与路由导航
- 查询条件与查询重置
- 列表分页、筛选、排序
- 新增、修改、查看
- 表单输入与前端校验
- 弹窗、抽屉、页签
- 树形选择及 Checkbox 授权
- 按钮启用和禁用状态
- 加载、空数据、失败及成功提示
- 页面之间的业务导航

原型可使用可控的模拟数据与 Mock API，但不得伪装为真实后端已接入。

### 5.3 源代码要求

- 代码结构清晰。
- 公共组件可复用。
- 设计 Token 可维护。
- 业务界面与 Mock 数据分离。
- 不使用不可维护的整页图片替代真实 UI。
- 保留供第四阶段替换 Mock API 的接口适配层。
- 原型代码作为第四阶段正式前端开发的基础。

原型统一放在仓库实际确认的 `mes-demo` 原型工程中，并建立功能编号与源代码目录映射。

### 5.4 浏览器验收

必须启动实际原型，在浏览器中完成：

1. 页面实际渲染检查。
2. 与设计稿的截图对比。
3. 菜单和页面路由检查。
4. 查询、编辑、保存模拟流程检查。
5. 表单验证检查。
6. 空状态及错误状态检查。
7. PC 及约定移动端视口检查。
8. 浏览器控制台异常检查。

### 5.5 G2 门禁

以下条件全部成立才允许通过：

- Vue 项目可以成功安装、编译和启动。
- 主要页面交互可正常操作。
- 实际浏览器测试已执行。
- 浏览器控制台无阻断性异常。
- 设计与实现的重大视觉偏差已修复。
- 已保存截图和测试报告。
- 已记录验收通过的代码提交号。
- 已形成有效原型确认记录。

若不通过，必须在第二阶段持续修复，不得进入详细设计冻结。

## 六、第三阶段 — 详细设计完善与开发基线冻结

第三阶段为独立强制阶段，不允许省略。

### 6.1 设计依据

以已确认原型、原始业务需求以及现有正式基线为依据，核对并完善：

- PRD 及业务需求
- 功能详细设计
- 页面详细设计
- 业务实体与关联关系
- 字段清单和数据类型
- 数据库 ERD、约束和索引
- 数据字典及选项来源
- 输入、输出、必填和校验规则
- 业务状态机及合法状态转换
- 权限资源与授权矩阵
- API 路径、参数、返回值和错误码
- 异常处理及幂等约定
- 业务审计及适用的 GxP 控制
- 测试用例、验收条件和 RTM

### 6.2 字段级设计标准

每个字段至少明确：

- 字段标识及中文名称
- 所属实体和页面
- 数据类型、长度、精度
- 是否必填及默认值
- 数据来源或数据字典
- 输入约束与校验规则
- 可见、可编辑条件
- 保存及更新规则
- 异常提示或错误码

如涉及数据库变更，必须设计增量 Flyway Migration，不得直接修改已经执行的历史迁移文件。

### 6.3 API 与权限标准

每个业务操作必须对应：

- 页面操作入口
- 操作权限编码
- 后端权限校验
- API 契约
- 状态和数据校验
- 成功及失败处理
- 对应测试用例

管理权限必须覆盖约定的新增、修改、删除及其他管理操作；只查看权限不得越权执行写操作。特殊操作单独定义，不允许含糊继承。

### 6.4 基线冻结要求

形成唯一的功能冻结清单，关联以下版本：

- 设计稿版本
- 原型源代码提交号
- 详细设计版本
- 数据库设计与 Migration 计划
- API 契约版本
- 权限矩阵
- 测试用例版本

生成冻结记录，包含功能编号、负责人或批准主体、冻结时间、文件校验信息及关联 Git 提交号。

### 6.5 G3 门禁

必须检查：

- 字段定义是否完整。
- 页面、数据库、API 字段是否一致。
- 操作按钮与权限是否一致。
- 状态机与后端业务规则是否一致。
- 异常和边界条件是否覆盖。
- 测试用例是否能追溯到需求。
- 原型与设计文档是否存在冲突。
- 冻结记录是否有效。

存在未解决的重大冲突、关键字段缺失或必需设计文件缺失时，禁止进入第四阶段。

## 七、第四阶段 — Codex 业务开发

### 7.1 强制开发约定

Codex 必须读取：

- `AGENTS.md`
- 对应功能任务卡
- 冻结版设计文档清单
- 原型源码位置与提交号
- API、权限及测试规范

Codex 的职责：

1. 直接复用已验收 Vue 原型代码。
2. 将 Mock 数据替换为真实 API。
3. 实现 Spring Boot 业务逻辑。
4. 实现 MyBatis-Plus 数据访问。
5. 完成数据库迁移和数据约束。
6. 接入权限、校验、状态机与异常处理。
7. 完成适用的审计及电子签名要求。
8. 编写并执行自动化测试。

### 7.2 禁止事项

- 不得删除原型后重新制作 UI。
- 不得随意更换前端框架或组件库。
- 不得修改冻结页面布局。
- 不得擅自修改颜色、字体或组件风格。
- 不得绕过后端权限校验。
- 不得跳过 Migration 直接修改生产数据库。
- 不得使用假数据冒充集成测试结果。
- 不得擅自修改冻结业务状态机与 API 契约。

如实现阶段发现设计缺陷，必须提交设计变更，更新受影响原型、文档与冻结记录后再继续开发。

### 7.3 G4 门禁

检查：

- 所有实现与冻结基线一致。
- 原型源代码继承关系可追溯。
- 真实 API 已完成接入。
- Mock 不再用于正式业务路径。
- 后端权限与数据校验正常。
- Migration 验证通过。
- 单元测试和组件测试通过。
- 无阻断性安全或编译问题。
- UI 冻结部分未出现未经批准的修改。

不通过不得进入最终集成验收。

## 八、第五阶段 — 完整集成验收

必须执行以下测试：

1. 后端单元测试。
2. 前端单元及组件测试。
3. API 集成测试。
4. 数据库 Migration 验证。
5. 角色与功能权限测试。
6. 业务状态流转测试。
7. 真实业务场景与关联数据测试。
8. 浏览器端到端测试。
9. 正式页面与冻结原型的视觉对比。
10. 异常、边界、空数据和非法操作测试。
11. 根据业务重要性执行必要的回归测试。

对于菜单功能，还需要验证：

- 菜单权限与角色授权一致。
- 未授权用户不能访问页面和后端接口。
- 只查看用户不能执行管理操作。
- 管理用户可以执行其获准的操作。
- 刷新页面及重新登录后的授权状态正常。

### G5 最终门禁

必须具备：

- 所有必需测试有实际执行记录。
- P0 / P1 / P2 阻断性问题为零。
- CRITICAL / HIGH 安全问题为零，或按现有安全基线明确的例外审批机制处理。
- 无未批准的数据库、API 或权限契约变更。
- 正式页面与冻结原型无重大视觉偏差。
- 测试失败和跳过项有明确原因与批准记录。
- 形成完整验收报告。
- 功能任务状态可更新为 `ACCEPTED`。

未满足条件，不允许声明开发完成或正式验收通过。

## 九、自动化门禁控制

创建实际可运行的门禁检查脚本，而不只是 Markdown 检查清单。

至少支持：

`validate-workflow --feature <功能编号> --gate G1`

`validate-workflow --feature <功能编号> --gate G2`

`validate-workflow --feature <功能编号> --gate G3`

`validate-workflow --feature <功能编号> --gate G4`

`validate-workflow --feature <功能编号> --gate G5`

以上命令为期望的命令接口，实施时根据现有工程技术栈提供真正可执行的实现。

每个 Gate 必须：

- 检查上一阶段是否通过。
- 检查必要交付文件是否存在。
- 检查交付文件的版本及关联关系。
- 检查所需测试的执行结果。
- 检查冻结状态及未经批准的变更。
- 检查是否存在阻断性问题。
- 输出结构化 JSON 报告和可读报告。
- 校验失败时返回非零退出码。

测试报告须有真实测试来源，不能靠手动将 `passed=true` 写入文件就绕过。

GitHub Actions 应根据修改的功能范围运行相应门禁。对新增功能的合并请求必须进行检查；正式分支保护和必需检查配置如需 GitHub 权限，应明确报告配置状态。

工作流脚本不应声称能够通过代码自动判断审美是否合格；视觉验收必须依靠浏览器截图对比、实际测试证据及有效确认记录。

## 十、阶段状态机

统一使用以下状态：

- `NOT_STARTED`
- `IN_PROGRESS`
- `REVIEW_PENDING`
- `BLOCKED`
- `REJECTED`
- `ACCEPTED`

每个阶段独立管理状态。

状态推进原则：

1. 开始阶段后为 `IN_PROGRESS`。
2. 交付物完整后为 `REVIEW_PENDING`。
3. 门禁与批准均满足后为 `ACCEPTED`。
4. 发现阻断问题时为 `BLOCKED`。
5. 验收不通过时为 `REJECTED`。
6. 修复后重新执行阶段检查。

只有上一阶段 `ACCEPTED`，才能启动下一阶段。

不得将自动化脚本通过等同于业务负责人确认。批准主体必须来自真实的用户确认、明确授权的代理验收机制或可核验的审批记录。

## 十二、Skill 自动执行策略

`mes-feature-workflow` 是主控 Skill。

每次启动时：

1. 识别功能编号及业务范围。
2. 读取最小必要基线。
3. 判断新建功能还是受控变更。
4. 选择需要执行的阶段。
5. 检查上一阶段门禁。
6. 调用或安排对应阶段工具。
7. 生成阶段交付物。
8. 运行本阶段检查。
9. 保存结果与证据。
10. 满足条件才允许进入下一阶段。

角色分工：

- UI UX Pro Max：UI 规范与视觉方案。
- Product Design：Vue 可交互原型与浏览器视觉验收。
- 详细设计流程：文档完善、领域规则及基线冻结。
- Codex：复用原型并完成前后端业务接入。
- 验收流程：真实集成测试、视觉一致性及最终交付。

跨 ChatGPT Work、Product Design 与 Codex 的阶段交接，必须使用可核验的源代码、设计文件、报告及 Git 提交。不能把不同工具间的协作描述成实际上并不存在的自动调用。

## 十三、变更控制

已经冻结的设计和原型发生变更时：

- 建立 Design Change / RFC。
- 明确影响的页面、实体、字段、API、权限和测试。
- 根据影响范围重新打开有关阶段。
- 更新所有受影响文档。
- 重新冻结并生成新的基线标识。
- 重新运行受影响的门禁与回归测试。

无影响范围分析，不得直接修改冻结内容。

## 十四、工作流自身的验收测试

创建工作流后，不得仅检查 `SKILL.md` 是否存在。

必须完成：

1. Skill 能被正确发现和读取。
2. 新增菜单任务能正确触发流程。
3. 新增功能任务能正确触发流程。
4. 修改页面模板任务能正确触发流程。
5. 缺失原型时 G2 必须失败。
6. 原型未验收时 G3 必须失败。
7. 字段和 API 契约不一致时 G3 必须失败。
8. 未冻结基线时 G4 必须失败。
9. 未通过集成测试时 G5 必须失败。
10. 完整模拟交付物和有效证据时，各门禁能够正常通过。
11. 检查脚本的失败退出码与 GitHub Actions 执行结果一致。
12. 原有工程规范、数据库迁移与业务代码不受本次初始化影响。

上述测试须使用独立的测试功能编号和测试数据，不得伪造真实业务验收记录。

## 十五、实施范围及最终输出

本次任务仅创建工程治理规范、Skill、模板、校验脚本及相关测试。

禁止借此机会修改 MES 业务功能、数据库表、Flyway Migration、正式页面样式及业务 API。

完成后输出：

1. Skill 实际安装路径。
2. 新增与修改文件清单。
3. `AGENTS.md` 中新增的强制规则。
4. 五阶段执行及验收标准。
5. G1–G5 门禁验证报告。
6. GitHub Actions 配置及实际启用情况。
7. Skill 触发与读取测试结果。
8. 工作流模拟测试结果。
9. 尚未具备的工具或权限及阻断说明。
10. 后续新增功能时的标准启动命令。

**完成标准：不只是建立一份流程说明，而是形成可执行、可检查、可追溯、可复用的 MES 五阶段工程工作流。**

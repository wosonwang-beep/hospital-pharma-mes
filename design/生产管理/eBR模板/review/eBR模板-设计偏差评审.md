## 原始设计图的必须保留结构

1. **深海军蓝左导航/顶部**，灰白工作背景与克制的医疗蓝主操作。
2. 页面首屏包括标题、状态条及**工作台主体**，不是先堆叠多块“版本信息、操作表单”卡片。
3. **三栏设计器**：左栏字段组件（文本、数字与单位、设备/物料扫码、电子签名、公式计算等）；中央模拟实际批记录表单所见即所得画布；右栏当前字段属性（名称、编码、类型、上下限、必填、越限偏差、校验）。
4. 中央工作区展示明确的工序标题、设备确认、工艺参数及操作确认三个分组，输入框按业务结构对齐；可选择画布字段并在右栏同步编辑属性。
5. 1440×1024 PC 下，三栏无需全页横向滚动；重要编辑区域在首屏清晰可见。

## 直接从当前源码查出的偏差（不是已完成浏览器测量）

| 对照点 | 原始设计 | 当前源码 | 结论 |
|---|---|---|---|
| 主体位置 | 顶部信息下立即进入三栏工作台 | `TemplateDetailView.vue` 先渲染大面积“版本信息”和“受控操作”，再进入 `DefinitionDesigner` | **重大视觉结构偏差**，设计器在页面中的优先级被降低 |
| 字段区内容 | 首屏少量常用字段入口，尺寸统一 | 左栏罗列章节/分组/表单/全部字段类型/批记录组件/规则/签名/复核按钮 | **信息密度失控**，需要分组或收纳，但保留全部业务能力 |
| 中央结构 | 工序/分组/字段是所见即所得的结构关系 | `DefinitionDesigner.vue` 分别循环 `definition.sections` 与 `definition.forms`，形成分段平铺 | **业务界面层次偏离**，需绑定工序、组和表单在同一画布呈现 |
| 右侧属性 | 常用字段名、数据类型、上下限、验证和签名等明确层级 | `attributes[kind]` 通用属性表单，部分 JSON/内部码直接呈现 | **默认展示过于技术化**；高级参数应合理收纳，不得删除 |
| 全局视觉 | 深蓝顶部、216px 深蓝左导航、医疗蓝 | 当前全局 `AppLayout.vue` 使用 256px 浅色侧栏 | **跨页面视觉基线冲突**；不能单独修改 eBR 而导致与全局方案矛盾 |

## 修复约束与实施次序

- 优先使用原始交互原型作为视觉参照，避免重新做“相似稿”；仅对已明确更新的业务字段、权限和 GxP 规则进行必要兼容。
- 先把当前 eBR 页面调整为设计稿三栏优先结构，再整理左字段库和右属性面板，使首屏实际画布可用。
- 保存/校验/提交/批准/电子签名的受控后端流程不能为了好看而移除；若原图缺少现行必需控制，应设置不影响主画布的清晰操作入口。
- 使用 1440×1024 的真实 5173 页面截图并列比较；逐项标注偏差后继续整改。
- 仍须进行 PC 页面交互审查：新增字段、选择字段、修改属性、拖拽排序、编辑取消、错误反馈、保存，不能把 HTTP 200 算成 UI 验收。
- 仅在有真实原型截图、实施截图和差异闭环证据之后才可标记“页面已验收”。

**本评审只完成原稿定位与源码结构比对；真实浏览器对照和代码改版尚未完成。**

## 第一轮实施后的视觉复评（PC 1440×1024）

**真实源码修改**：
- `TemplateDetailView.vue` 把三栏设计器提前到版本及受控操作卡片之前，补充顶部保存/校验/原因区；保留审批、发布、历史证据操作。
- `DefinitionDesigner.vue` 的组件库分为常用字段和可展开的高级/批记录/规则字段；完整现有业务字段类型仍在。
- 中央画布根据现有 `groupCode` 将字段按“设备确认 / 工艺参数 / 操作确认”等现有组渲染为真正的表单分组；右侧属性优先展示常用配置，其余可展开。
- 当前视觉预览采用浏览器加载**实际 Vue 组件**、只 Mock 接口所需的展示数据；不是真实登录与业务持久库验收。模拟测试本身不发起业务写操作。

**截图**：
- `eBR模板-设计-实现预览-模拟数据.png`：修改后 Vue 1440×1024 的样例视觉截图。
- `eBR模板-设计-同屏对照.png`：与 1440×1024 冻结原稿并排的像素尺寸对照；源页 HTML：`eBR模板-设计-同屏对照.html`。

**实际检查过的布局**：左组件栏 x=280, y=297, w=210；中画布 x=504, y=297, w=616；右属性栏 x=1134, y=297, w=282；主文档无横向溢出。这证明工作台已回到首屏，但不是像素级100%一致。

**尚未消除的视觉差异**：
1. 全局 Shell 仍是当前批准的 UI V2 白色/浅灰导航（256px），原稿是深蓝导航（216px）；涉及全系统统一外观，不能擅自仅改 eBR 一页。
2. 原稿右栏展示字段数值上下限等专用参数，当前 DTO 部分规则以 `validationJson` 存储，需要进一步核对业务字段来源并设计安全易用的可视编辑方式，不得假造未存在的数据。
3. 原稿中“操作人签名”是模拟示意，当前 `SIGNATURE_PLACEHOLDER` 只代表模板签名占位；正式受控签名必须继续走已存在的后端受控流程，不能仅通过预览按钮伪造。
4. 尚无使用**真实开发库 eBR 模板**在当前已登录浏览器中完成全量 CRUD/受控操作与截图对照的证据。

**结论：首屏三栏及业务分组的设计一致性明显改善，仍为「设计整改中，未验收」；禁止标记 100% 完成。**

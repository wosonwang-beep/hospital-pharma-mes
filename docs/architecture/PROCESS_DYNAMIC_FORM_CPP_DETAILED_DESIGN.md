# 生产工艺动态表单 CPP 规则详细设计

状态：`APPROVED DETAILED DESIGN / NOT IMPLEMENTED`  
对应需求：[PROCESS_DYNAMIC_FORM_CPP_REQUIREMENTS](../development/PROCESS_DYNAMIC_FORM_CPP_REQUIREMENTS.md)

## 1. 设计定位

CPP 规则是生产工艺中工序动态表单定义的组成部分。设计器复用现有动态表单字段和安全 DSL 能力；CPP 页签不建立产品主数据副本，不承担生产运行模拟。

```text
ProductionProcess
  └─ Operation
      └─ DynamicForm
          ├─ Field[*]
          └─ CppRule[*]
              ├─ ConditionTree
              └─ ExceedAction[*]
```

## 2. 页面详细结构

### 2.1 页签

- `表单设计`：保持现有字段和画布职责；字段库中每一个可插入字段前显示独立 `+` 图标。用户先在 Canvas 中定位光标/选区，再点击对应字段前的 `+`，系统恢复该画布位置并将字段插入当前位置；点击字段名称本身不再作为插入动作。
- `CPP规则设计`：规则列表/选择、当前字段、规则编辑和预览。

两个页签共享当前生产工艺、工序和动态表单上下文。切换页签前应保存或明确处理未保存更改。

### 2.2 CPP 规则设计页签

已批准并实施的三栏主工作区：

- 左栏“当前动态表单字段”：显示当前表单字段名称、编码、类型、单位，并提供只读搜索；字段只选不改；
- 中栏“CPP规则可视化配置”：规则基本信息、条件树、AND/OR 条件组、业务预览、安全 DSL 预览和超限动作；
- 右栏“规则说明 / 本表单CPP规则 / 当前上下文”：用于规则切换、启停和说明，不重复维护字段或产品适用关系。

窄桌面视口可按专用设计器规则重排，但字段区、配置区和预览/动作区的职责不得合并或丢失。页面不得出现“适用产品”和“运行校验效果”。

## 3. 逻辑数据模型

本节保留概念上的 CPP 规则/条件/动作结构。实施复用评审已完成：物理层不新增第二套 CPP 三表，直接复用现有 `ebr_rule_def` 与安全 DSL；仅通过追加 Flyway V064 为 `ebr_rule_def` 增加 nullable `cpp_config_json`，用于保存可视化设计器元数据。现有 `expression` 继续作为服务端 lint/执行的唯一规则表达式来源，历史行保持 `cpp_config_json=NULL`，不改变旧发布 canonical/hash。

### 3.1 `ebr_cpp_rule`

| 字段 | 说明 |
|---|---|
| id / org_id | 主键与组织隔离 |
| form_def_id | 所属当前动态表单定义 |
| rule_code | 模板生命周期内稳定编码 |
| rule_name / description | 业务名称与描述 |
| expression | 由条件树规范化生成的白名单 DSL |
| preview_text | 与表达式同版本生成的业务预览 |
| active_flag / sequence_no | 启用和顺序 |
| version_no | 乐观锁 |

禁止 `product_id`、产品编码或其他产品直接绑定列。

### 3.2 `ebr_cpp_rule_condition`

| 字段 | 说明 |
|---|---|
| id / cpp_rule_id | 条件节点及所属规则 |
| parent_id | 父条件组；根节点为空 |
| node_type | `GROUP` 或 `CONDITION` |
| logical_operator | 条件组使用 `AND` 或 `OR` |
| field_def_id / field_code | 条件项引用当前表单字段及稳定编码 |
| comparison_operator | 按字段类型允许的比较运算符 |
| operand_json | 类型化比较值，不存任意脚本 |
| unit_id | 数值比较单位；必须可验证兼容 |
| sequence_no | 同组内顺序 |

约束：条件组至少一个子节点；条件项必须有字段、运算符和值；所有字段必须属于 `form_def_id` 指向的同一表单。

### 3.3 `ebr_cpp_rule_action`

| 字段 | 说明 |
|---|---|
| id / cpp_rule_id | 动作及所属规则 |
| action_type | 本次批准：`MARK_EXCEPTION`、`BLOCK_SUBMIT`、`CREATE_DEVIATION`、`REQUIRE_QA_REVIEW` |
| action_config_json | 动作必要的受控配置；不得保存脚本 |
| active_flag / sequence_no | 启用和执行顺序 |

同一规则的同类动作只能有一个活动配置。动作配置不得复制角色、权限、签名或偏差主数据。

## 4. 条件树与表达式生成

### 4.1 规范化流程

1. 校验规则只引用当前表单字段；
2. 按字段数据类型校验运算符和值；
3. 校验单位相同或存在受控转换；
4. 按条件组顺序生成带显式括号的中间树；
5. 生成白名单 DSL；
6. 通过现有 DSL parser/lint；
7. 从同一条件树生成业务可读预览；
8. 保存条件树、DSL 和预览，避免三者由不同输入独立维护。

示例：

```text
条件树：AND(GE(ster_temp,121), LE(ster_temp,125), GE(ster_time,20))
DSL：(value('ster_temp') >= 121) && (value('ster_temp') <= 125) && (value('ster_time') >= 20)
预览：121℃ ≤ 灭菌温度 ≤ 125℃，且灭菌时间 ≥ 20min
```

业务预览不得作为执行输入；执行只使用经 lint 的规范化规则定义。

### 4.2 安全规则

- 仅允许现有 DSL 白名单中的字段引用、常量、逻辑和比较能力；
- 禁止前端提交任意表达式绕过条件树；服务端必须重建或验证表达式等价性；
- 设置表达式长度、节点数量、嵌套深度和求值步骤上限，具体数值在实施合同中锁定；
- 发布前检测未知字段、循环依赖、空组、非法类型和不可转换单位。

## 5. 保存、发布与冻结

- 草稿保存：在同一事务内保存规则、条件和动作，并使用现有组织隔离、权限、幂等、乐观锁和审计机制；
- 提交/生效：运行静态 lint，任一错误均阻止状态推进；
- 冻结：生产批下达时，CPP 规则连同字段标识、条件树、规范化表达式、动作和引擎版本进入现有定义快照/摘要边界；
- 历史：新规则或新工艺定义不改变已下达批次的快照、执行结果、偏差、签名或审计证据。

## 6. 运行阶段职责

设计页不执行真实运行校验。生产/eBR 运行阶段在现有触发点按冻结定义求值，并记录规则编码、输入快照、通过/失败、动作、时间、引擎版本和规则版本。

动作映射：

| 动作 | 运行行为 |
|---|---|
| 标记异常 | 在当前表单/工序状态中形成可追溯异常标记 |
| 禁止提交 | 规则失败时拒绝表单提交 |
| 生成偏差记录 | 调用现有受控偏差入口，保证幂等 |
| 要求 QA 复核 | 创建/呈现现有 QA 复核要求，不复制 QA 权限模型 |
> 本次最终批准页面不包含“阻止工序完成”和“要求电子签名”两个 CPP 动作；现有工序完成门禁、签名/重新认证机制保持原样，未被删除或弱化。

## 7. 接口与权限边界

本次设计不批准新的独立顶层路由或权限体系。正式实施优先扩展现有生产工艺/动态表单定义的读取、草稿保存和 lint 合同；如现有合同无法表达条件树和动作，必须在实现前补充精确 API/OpenAPI 与权限影响记录。

服务端必须校验：组织归属、工艺/工序/表单关系、草稿可编辑状态、字段所有权、规则代码唯一性、乐观锁、权限、DSL 安全和动作配置完整性。

## 8. 实施与测试影响

- UI：生产工艺工序动态表单设计器新增 CPP 页签；
- Domain/Application：条件树校验、规范化生成、规则/动作保存和冻结；
- Database：复用 `ebr_rule_def`，V064 仅追加 nullable `cpp_config_json`；
- API/OpenAPI：复用现有定义读写/lint 接口，`Rule` 仅新增可选 `cppConfigJson` 字段，不新增顶层端点；
- Runtime：复用现有规则引擎和证据表，按最终批准的四类 CPP 动作映射；
- Tests：字段归属、AND/OR/嵌套组、类型/单位、表达式安全、动作组合、状态/权限/并发、快照不变性和历史兼容；
- UI 验收：仅桌面端按批准视口执行原型比对、完整任务流和 G5 审查。

原型版本已获确认并完成本轮增量实现；是否达到 `READY FOR ACCEPTANCE` 仍以真实 5173/8080、G5 UI/UX 审查及最终人验为准。

## 二、岗位目标与业务判断（产品经理）

| 岗位 | 进入系统首先需要看到 | 本职主操作 | 业务结果与交接 |
|---|---|---|---|
| 主数据/工艺维护 | 在用物料、产品、处方、工艺及其适用关系 | 编辑当前有效定义，关联工序和表单/CPP | 可用定义与生产批冻结内容一致 |
| 仓库 | 到货批号、数量、检验/库存状态、可执行出入库 | 收货、取样交接、入库、发料/退料 | 每物料批或成品批准确流转，不以整单状态替代批次质量 |
| 取样 | 已安排任务、物料批、取样量及位置 | 取样与样品交接 | QC 接收样品并能直接进入检验 |
| QC 检验/复核 | 样品、项目、方法/标准、结果及待复核状态 | 录入结果、复核、报告 | 结果完整、状态可定位、交由 QA 判断 |
| 生产 | 当前生产批、工序、CPP 与待填 eBR | 按工序完成记录与复核 | 工序完成、数量/平衡可核、交质量与仓储 |
| QA | 批次、所有真实阻断项、待签决定 | 满足条件后直接批准/拒绝 | 放行决定唯一且可追溯，后续归档不重复审批 |
| 系统管理 | 用户角色、菜单/打印等当前配置 | 配置和查询权限/模板 | 常用权限可见且动作含义明晰 |

以上岗位目标属于基于系统合同的产品走查，并非新做过的岗位访谈。

## 三、问题分级与总体结论

P0 = 严重误导核心业务结论或阻碍关键闭环；P1 = 影响完成任务、易错或反复跳转；P2 = 重要但可迭代优化的名称、表达和呈现问题。源码测试成功、API 能返回及首屏美观都不能单独抵消业务错误。

当前有 **一个已复现的 P0 信息可信度问题、多个 P1 业务路径/数据表达问题**。不建议扩张新功能；按以下明确问题收敛整改。优先级不意味着授权变更数据库、签名或历史证据。

## 四、高优先级问题清单（可直接转整改任务）

### PM-001｜P0｜生产批360°视图异步阶段显示错误业务结论
**事实**：批次 HYTEA-20261109-002 已 QA_RELEASED。真实浏览器页面在首次0.8秒和累计约3.3秒仍显示产品=2、单位=3、工序进度=0/0、质量未读取、平衡暂无结果，累计约8.3秒才显示产品=喉咽茶合剂、单位=毫升、工序8/8、质量条件满足、平衡1/1；没有真实数据丢失的证据。
**影响**：操作员可能判断已完成工序尚未做、物料平衡未计算，重复寻找或执行工作。
**代码**：ProductionDetailView.vue:21、BatchOverview.vue:15-20、33-39、55-65，引用 API 并行读取却把“尚未返回”计算为0/无结果。
**建议**：加载期间只显示“正在读取/未完成核对”，禁止展示0/0和“暂无结果”等事实性结论；每个卡片独立加载与错误提示，完成后显示准确业务名称、单位、状态和继续按钮。必须区分未知/空/不通过。
**验收**：批655在慢网、API成功、API500、切换批次时不出现虚假业务结论；最终8/8、1/1和QA放行与真实来源一致。

### PM-002｜P1-HIGH｜生产检验样品选择器初始化即报400
**事实**：/quality/production-tests 查询区样品控件显示红色 Invalid ID；真实 GET /api/v1/samples HTTP400。即使用户未选择生产批也已报错。
**代码根因**：ProductionQualityList.vue 的样品选择器传入初始 mainBatchId 空字符串；IncomingReferencePicker.vue:50-52 将其作为过滤参数传给 /samples；ProductionQualityService.java:35 在过滤值存在时调用 MasterMutation.id(空字符串)，抛 Invalid ID。
**建议**：未选生产批时不发送空ID过滤；依据实际规格选择不依赖批次的合法样品列表或明确提示先选生产批；选择批次后刷新样品列表和禁用无效关联。不得通过删除查询控件掩盖错误。
**验收**：初始页无错误；选择和清空批次、快速切换、空结果、输入查询均无400且符合真实候选数据。

### PM-003｜P1-HIGH｜生产工艺页面与批准交互仍存在验收欠账
**事实**：当前 /process/packages 列表可打开，但可见多条“未命名（历史工艺）”，操作列还有不必要的历史版本/批准日期技术信息。既有 MES_TASKS.md 记录此前工艺正式页面对原型的路线、角色、工序表单层级等保真返工曾为 REWORK_REQUIRED；本轮只查清单与典型只读详情，不能替历史验收签字。
**建议**：以当前获准的工艺→工序→表单及表单内CPP规则为唯一业务主线，对照已冻结原型逐一关闭差异。把历史未命名实例明确归类、减少干扰；不能为了清爽物理删除有业务关联的记录。
**验收**：用户进入在用工艺即可明确工序顺序、每工序几张表单、设计表单入口及CPP规则；保存/返回/异常恢复真实验收，历史记录不影响在用工艺选择。

### PM-004｜P1-HIGH｜检验单据“业务编号”使用长技术标识
**事实**：/quality/inspection-requests 列展示 IR-4871f64a... 等哈希式编号；检验任务详情标题显示 IT-bd298...；样品 SP-a02...，人员需反复比对批号才能识别同一业务链。
**建议**：表格优先展示物料/产品+批号、请验类型、状态及关键时间；技术主键/哈希移入按需查看的追溯详情。若需引入新短单号，须明确已有单号与唯一性合同后单独审批，不能悄改已签历史。
**验收**：同一批的请验→取样→检验→报告可连续定位；不依赖复制长哈希。

### PM-005｜P1｜检验记录与收货表格可读性不足
**事实**：检验记录 /quality/inspection-tasks 在1280首屏部分列出现逐字符换行，检验任务状态、样品号和操作列被压缩；/wms/receipts 的仓库/状态/操作列同样狭窄。
**建议**：按业务顺序稳定展示物料名/批号、样品/检验人、结果、状态、操作；将低频字段移入只读详情，保持“查看”可见，不让重要列垂直逐字排列。数量按单位显示合理小数精度，完整原值可在详情查。
**验收**：1280 PC 分辨率首屏能识别每行对象、状态与动作；1440/900不遮挡、不无提示横向滚动。

### PM-006｜P1｜QA已放行却仍叫“进入QA审核”
**事实**：/finished/qa-reviews 列表包含已QA放行的批655，行操作仍写“进入QA审核”；源码 NavigationEntryList.vue:39 对所有 qa-review 行使用固定文字。
**影响**：用户误以为要再次审批，与批655既有决定690及签名5348矛盾。
**建议**：按状态和实际 allowedActions 区分“去审核待处理批次”和“查看已放行决定/归档证据”；已放行批次不再出现误导性的待审批动词。成品放行入口明确与QA批审核的不同任务，不重复开发QA决策。
**验收**：待审/已放行/拒绝/无权四种状态的名称与下一步一致，已放行批次仅只读访问历史，不重签。

### PM-007｜P1｜首页占位任务卡抢占首屏
**事实**：DashboardView.vue:33 将“待处理任务”硬编码为“未提供”，:69 的“我的待办”表永远显示“暂无可用的个人待办数据”，却在首页占据显著面积。其余生产、质量、仓库入口确有真实业务对象。
**建议**：未提供可靠待办数据时去掉突出占位卡；或复用现有业务合法待办来源，不自行制造统计。首屏以当前角色最常完成的具体任务和下一步为中心，不展示技术未实现状态。
**验收**：没有待办时明确“无待处理”或不展示该模块；数据未接入不得称0任务，也不显示“未提供”作为KPI。

### PM-008｜P1｜跨模块入口名称与真实业务职责不一致
**事实**：侧栏“质量调查”打开后标题为“来料调查”，内部却提供“质量范围”选择；侧栏“生产订单”的 H1 为“历史生产订单”；侧栏“生产批”的 H1 为“生产指令 / 生产批”。同一个对象在不同位置的命名缺乏主词。
**建议**：统一单据业务名；若生产订单在当前模式仅用于查旧记录，导航应明确“历史生产订单（查询）”；生产批仍以“生产批”为主对象。质量调查范围应在页标题或显著筛选标签体现是来料还是生产，避免QC岗位误解。
**验收**：从侧栏、面包屑、列表、详情返回时，同一业务实体的名称和入口一致。

### PM-009｜P1｜检验详情数据来源与完成状态并列显示“待读取”
**事实**：已完成且检验合格的检验记录详情仍出现“物料批量 5000.000000 单位待读取”“计划取样量 未记录”“实际总取样量 未记录”，顶部却以长IT哈希为主标题。
**建议**：把业务编号、物料/批号、检验结论与复核者置于显著位置；数量单位引用返回前显示加载中；事实缺失显示“来源未提供”，绝不能补“合格”或猜测取样量。
**验收**：状态完整的业务单据无内部解析占位；真实缺数据有来源和去补录入口，不影响已签检验事实。

### PM-010｜P2｜设备模块身份与主数据编码显示不友好
**事实**：侧栏“设备”的页面 H1 为“设备与人员资格”，同时侧栏另有独立“人员资格”；设备列表显示 ELECTRONIC_SCALE、PRODUCTION_SCALE、DEMO_SCALE 等代码。
**建议**：本页业务标题只称“设备”，资格管理保持独立菜单。字典枚举显示经批准的中文名；既有业务数据中不适合的类型值须先核对引用及来源，不因名字难看直接批量删除。
**验收**：设备页面首屏只回答“设备是什么、是否能用、校准是否有效”；角色不会误以为在此维护资格。

### PM-011｜P2｜角色配置存在不可见的已选权限
**事实**：管理员角色详情明确提示“已选权限中有5项未在可用目录展示，保存时会保留”；普通菜单权限表只显示其他项。
**建议**：在“未在当前目录展示的权限”下列出明确中文名称、来源和用途，允许只读查看，不能暗自授予或撤销；已批准的两级只查看/管理选择继续保持。
**验收**：任何角色权限变更前能解释实际生效内容，不隐藏必要信息，也不恢复被废弃的审计菜单。

### PM-012｜P2｜业务数量与日期的显示不统一
**事实**：收货量显示 5000.00000000，检验样品量显示 1.00000000；检验详情写“检验时间 (UTC)”，其他页面多为本地日期。多处使用原始ID和英文状态或技术类型编码。
**建议**：由受控单位的显示精度决定千克/瓶/毫升的格式，保留底层实际数量；时间统一采用业务所在时区并明确说明；用户可见文案中文优先，技术字段仅技术证据区按需展示。
**验收**：同一量在收货、领用、检验、库存和归档中单位与数量一致、没有凭空换算。

### PM-013｜P2｜电子批记录配置入口可发现性需验证
**事实**：生产管理当前真实后台菜单列出5个主入口；源码中存在工序表单和批记录模板维护路由，但没有同等独立侧栏入口。本轮生产工艺详情可见“工序表单”“新建工序表单”入口。
**判定**：这可能是用户批准的“工艺内统一维护表单”方向，不能直接判为缺陷。
**建议**：把工艺→工序→设计表单→CPP规则→保存/生效逐动作核对；若入口可完成工作，无须为每个后端实体增加菜单。需要直接维护批记录册时明确其业务位置，而非增加重复入口。
**验收**：不依赖用户记住技术模块名，能从当前工艺直接完成表单与CPP设置。

### PM-014｜P2｜完整G5与真实角色可用性尚不可宣称
**事实**：本轮通过的是管理员下的菜单入口和代表详情只读浏览；没有在仓库、生产、取样、QC复核、QA等独立岗位逐一进行新业务提交/取消/异常恢复。页面曾有“禁止抽屉式操作”整改，当前源码扫描活动Drawer为0。
**建议**：后续仅对本清单的具体缺陷与真实岗位执行必要的有界复验，不重新重复已经完成的DEV批655 QA放行/归档，不将源代码单元测试当成实际岗位验收。
**验收**：每个整改项按其实际影响的岗位和页面测最小正/反路径，记录浏览器和API证据。

## 五、跨模块任务闭环与页面职责建议

**来料质量**：到货收货 → 每物料批请验 → 取样/仓储交接 → 样品接收 → 检验结果 → 独立复核/报告 → QA判断 → 库存状态。现有菜单链条齐，但编号和重复筛选造成跨页定位困难；应靠物料批上下文跳转、业务名称/批号和状态传递，而不是复制哈希或重新选择同一对象。

**生产**：在用产品/工艺/处方 → 创建生产批 → 工序/CPP/eBR → 质量与平衡 → 生产完成 → 成品入库。现有路径基本覆盖，但“生产工艺”和“生产批360°视图”直接影响流程可靠性；不要把正在加载的技术数据误表达成“没有执行”。

**成品**：入库申请 → 仓库确认 → 成品请验、取样、检验 → QA决定 → 可用库存 → 发货/最终归档。现有菜单将“QA批审核”和“成品放行”分成两个入口，需区分岗位任务，而不是同一已放行对象在两个列表重复提示“去审核”。

**管理**：基础资料优先支持生产/检验上下文引用；角色只查看/管理级别保持；打印模板/数据源配置只作为专职配置工作，不应成为常规仓管/生产/QC操作的前置学习内容。

## 七、业务产品经理推荐的整改顺序

| 批次 | 待办 | 涉及页面 | 最小实施边界与复验 |
|---|---|---|---|
| 第1批：必须先修 | PM-001 详情加载假结论、PM-002 样品过滤400 | 生产批360、生产检验 | 只修读状态与过滤条件；不改生产状态机或QA签名；真实批655只读回归 |
| 第2批：闭环使用 | PM-004 业务识别、PM-005 表格可读、PM-006 QA动作、PM-009 检验详情 | 来料检验、收货、QA列表 | 业务对象/状态/动作真实展示；不改已签历史与技术主键 |
| 第3批：工艺保真 | PM-003、PM-013 | 生产工艺工序/表单/CPP | 逐项对照已确认原型和冻结业务合同，先关口径差异，不另起第二套设计 |
| 第4批：统一语言和入口 | PM-007、PM-008、PM-010、PM-011、PM-012 | 首页、菜单、设备、角色、单据详情 | 用户可见业务名称与技术细节分离，少量低风险呈现调整 |
| 独立验收 | PM-014 | 仓管、生产、取样、QC、QA主要场景 | 没有用户或角色实际操作的部分仍标 NOT RUN，不给虚假的整体验收 |

建议每个整改项统一满足“业务对象可定位→当前状态可信→主操作明确→异常可恢复→结果可返回定位”。对问题影响的角色定向验收，而非重复进行已经完成的批655生产、QC、QA流程。

**产品经理禁止扩张的内容**：不增加新的审批链、不为了验收重建角色和账号、不增加侧滑抽屉、不恢复审计菜单、不添加无数据来源的统计、不新增第二套工艺或单据模型、不启动手机端工作，也不把“用户确认原型”替换为技术方便的新界面。

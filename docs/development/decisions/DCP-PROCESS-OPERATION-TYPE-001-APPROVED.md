## 精确业务与数据合同

1. 在工序增加真实属性 `operationType`：`PRODUCTION`（生产工序）或 `IPC`（过程检验工序）。界面继续使用原型中的两种中文名称。
2. 对应 `proc_operation_def.operation_type VARCHAR(16) NULL`，仅允许上述两个值或NULL。通过新的append-only Flyway迁移增加；物理版本须按同一DEV库成功最大值分配，批准前不放入自动启动迁移目录、不执行DDL。
3. 存量行保持NULL，不按编码、检验项或名称自动回填。NULL表示历史未标注；界面显示「未标注」，不是第三种工序类型。维护人员选择后才保存标注。
4. 新界面新增生产/IPC工序时分别明确设置两种类型。类型变更不自动删除检验项、参数、表单、签名或前置关系，不自动清空角色/设备。
5. 兼容旧客户端：保存请求省略或传null时保留已存类型；原未标注行仍可按既有合同保存，不把全量历史标注变为强制前置条件。无效非空类型拒绝。类型不凭一次界面切换变更其他工序。

## API、快照及执行边界

- 既有 GET `/process-packages/{id}` 的 `currentDefinition.route.operations[]` 在有值时返回 `operationType`；PUT `/process-packages/{id}/current-definition` 接收该可选属性。路径、权限码、组织隔离、幂等和当前定义保存语义不变。
- 空值在序列化中省略，避免仅升级代码改变旧空类型的规范化内容。历史发布JSON/hash、生产冻结快照、签名、审计、谱系保持原件；不回算或覆盖历史。
- 后续新建快照可携带已明确保存的类型，供显示和追溯。类型本身不新增质量状态机或放行命令。
- 是否检查、如何判定及阻断哪些后续工序，继续由该工序的 `ipcDefinitions`、完成规则、必检/有效FAIL/独立复核/签名合同及前置依赖决定。不得新增「每套工艺必须有IPC」「所有工序均等待检验合格」等全局规则。
- 工艺仍维护当前定义，不恢复版本创建/提交/审批。eBR继续原有独立受控版本与签名流程。

## 4. 数据与状态待冻结设计

- **请求**：仓库事实、QC检验依据/版本/确认人/确认时间分属不同岗位；只让 QC 填批准标准，不允许仓管员在提交流程伪造质控数据。
- **取样**：QC计划取样量是计划值；检验员**实际取样量**及样品分配是实测值；仓管确认的实际出库量与逐容器实测总和在单位转换后必须相等。检验样与留样数量之和等于实取量，禁止无依据默认数量。
- **库存**：必须以组织+物料批+实际来源库位及容器为锁定边界；逐容器校验足额，无负库存；每取样明细唯一出库事件与请求幂等键，确认写入与取样完成要么全成功要么全回滚。
- **状态机**：QC确认请验时生成取样任务 PLANNED、检验任务 CREATED（业务上待样品）。取样员提交待仓管确认的正式受控状态/事件需决定是增加状态还是有独立交接凭证，但**绝不混同已完成取样与已出库**。样品 RECEIVED 才可以开始检验。仓库出库不影响质量 QA 放行结论。
- **角色**：仓管提交/仓管出库确认、QC选择标准/确认请验、取样员采集、检验员录入、独立复核/报告批准分别由后端权限校验，不以页面角色切换模拟授权。
- **历史**：已批准历史质量标准、已生成检验任务与样品、已确认取样、旧库存流水和签名不可追写或覆盖；数据迁移只追加且不可改已执行版本。

## 5. G1页面与原型设计边界（当前仅为产品方案）

- **T1 请验列表**：按角色区分“仓库待提交／QC待接收／已确认”，不是强行复制两张相同数据表；保留原列表和查询规则。
- **T2 仓库请验**：页面先展示检验对象/物料批/收货来源自动带出，再录请验数量、件数、理由；**不出现必填质量标准**；底部取消／保存草稿／提交请验。
- **T3 QC接收请验**：上部只读仓库来源、当前状态，中部“检验依据标准（已批准版本）／计划取样量、单位、件数及方案”，底部“退回补充（如有受控合同）／确认请验并生成取样单及检验任务”；要求生成后能打开两个记录。
- **T3 取样执行**：检验人员核对来源和方案，逐容器填写实取量、样品分配和复封，动作“提交取样记录，待仓管确认”，无库存扣减按钮。
- **T3 仓管确认样品出库**：只读采样事实，核对批/容器/库位/单位/数量，显示扣减前/本次/后库存；只允许仓管有权角色确认，不允许修改实测数据以凑余额。
- **T3 检验任务**：QC确认时已有任务编号和冻结检验项目；待样品阶段只读，样品接收后解锁原始检验数据/结果录入、检验员签名、送复核。
- **T3 检验报告**：由已复核结果自动汇总，不重复手工输入检验项目数据；报告复核和批准分别留痕，QA放行独立。
- **全局**：Global UI V2、T1–T6、PC端；所有标签/输入同一行；普通查询紧凑；子表增加按钮置于标题栏右侧；不新增无依据的菜单权限字典。

## 2026-10-19 最新决策：请验单一键自动生成（覆盖全部此前仓库请验新增方案）

**最高优先级用户指令**：收货页面只提供 **「生成请验单」** 按钮，**无新增请验弹窗**，仓管员不需要先手动填写请验单；系统从本次已确认收货记录与具体物料批次自动生成请验单及可追溯关联，随后送检验部门待确认。若有需要，用户才点击「查看请验单」「修改请验单」，进入已有受控页面；修改只开放当前状态、当前角色允许的字段，已确认 QC 冻结事实不可编辑。

- 一键操作：已确认且需要检验、尚无对应有效首次请验单的收货物料批次 → 服务端按物料批次、收货来源、仓库、生产企业/生产批号、数量、单位、包装件数等**真实已保存事实**自动生成首次请验请求；不得伪造取样结果或QC标准。
- 当前交付目标：一次点击 **生成并提交请验** 到 QC 待确认队列；页面返回真实请验单号与「查看请验单」入口。失败显示原因并保持收货原始记录不变；重复点击/网络重试应由服务端按同一批次的首次请验身份和幂等键确认既有结果，**不得重复创建**。复检/补充检验仍走独立受控流程，不受首次请验防重限制的粗暴阻断。
- 入参边界：前端只传被授权的已确认收货/物料批次引用和命令上下文，不通过页面重新手工提交收货事实，仓管员不需要选择标准。系统数量/单位取自已保存的实际收货明细与批准换算，不用在 UI 中猜测数量。
- 业务状态：自动生成的请验单可为一次性**已提交/待QC接收**（需与现有DRAFT/SUBMITTED记录控制及审计保持一致）；绝不因“生成”同时批准质量标准、取样计划、检验任务、样品或QA放行。QC确认时按上一节方案严格验证标准、计划取样量/单位，并原子生成取样单和待样品检验任务。
- 现有技术冲突 **CR-01 仍需 DCP 修改**：当前 `InspectionRequestCommand` 创建即要求 `qcSpecificationVersionId` 与手填数量，且 `createRequest` 立即冻结质量标准。必须引入受控的**收货批次一键请验**命令/阶段，仓库阶段不需要 QC 标准；QC确认阶段单独校验并冻结批准版本。不可仅给前端预填假版本或隐式将“首个标准”视为QC批准。
- 页面设计改动：**取消先前新建请验弹窗和独立仓库新增请验 T2 的所有 G1 草案**。收货详情在需要检验时放置单一主按钮「生成请验单」，生成后改为查看/必要时编辑。检验部门既有请验 T1/T2/T3 页面保持不重设计；取样记录列表/详情/打印、检验任务逐项结果/综合判定、独立审核签名、报告列表和打印保持本轮用户已确认要求。
- 此处确认的是**业务交互规则**，还不是新 API、数据迁移、设计图和交互原型的正式验收。须将最新G1页面稿与G2原型同步后，再依据项目规定取确切版本的用户批准、冻结G3并进入G4。不得把过期“收货弹窗请验”图当作批准稿。

## 2026-10-19 用户增量：必须提供四张T1列表、检验单类型与让步接收结论

**用户指出前稿遗漏全部列表**，原G1六张详情稿不得视为完整交付。本次按照Global UI V2/T1增加四张独立T1静态设计：请验单列表、取样记录列表、检验任务列表、检验报告列表。沿用现有质量菜单和正式路由，不额外创建无根据的模块。均需有查询/重置、状态筛选、分页、查看入口。取样记录须展示取样人/日期/计划和实际取样量/状态、查看/编辑/打印；检验任务应可从列表进入受控详情；检验报告列表应可查询及按允许状态打印。

- **检验单类型**：在检验记录T1和任务详情T3均显示，来源是父请验单 `requestType`，遵循既有字典 `INITIAL→首次检验`、`RETEST→复检`、`SUPPLEMENTARY→补充检验`、`INVESTIGATION→调查检验`。并同步显示在报告列表/详情，不能由检验员在任务中自由改写。
- **综合检验结论**：展示 **合格 / 不合格 / 让步接收**；结果未填全、未复核或不可判定时应显示**待判定**，不是第四种最终批准结论。项目检验原始结果的 `PASS/FAIL/INCONCLUSIVE` 继续按真实标准判定并保留不可变证据。
- **让步接收**：用户要求其作为可见业务结论，但当前冻结的原始项目结果/报告枚举不具备任意 `CONCESSIONAL_ACCEPTANCE` 状态，且QC人员不得通过勾选让步接收将某个原始FAIL改写为PASS。此为**CR-08 正式合同新增候选**，须有适用范围、偏差/OOS调查、授权质量决定、审批人签名及记录留痕；不允许未经QA批准就标作有效接收或使 BLOCKED 库存变 AVAILABLE。若关键质量标准不允许让步接收，应阻断该选择，不能用放行绕过强制质量要求。
- **显示与记录层区分**：列表/详情显示用户指定的「让步接收」字段选项是G1产品展示；是否成为检验报告正式 `overall_result` 枚举、独立 disposition、或QA决定显示名称，必须经过G3数据/状态/审计决议；不能仅修改前端文案并在服务端偷存 FAIL/PASS 冒充批准结论。
- 新增检查 **NQ-10**：检验任务和报告的T1/T3均有检验单类型且来自请验类型；最终三种结论以及待判定显示与审批状态一致，只有批准的受控让步接收具备有效质量决议引用。未获正式审批前仅静态样例，不能更改正式QC/QA行为。

## 2026-10-19 用户增量：检验记录先按样品名称与批号识别，检验单号等同报告号

本节覆盖上一节中“让步接收直接作为检验任务综合结论”的展示表述，但不删除其历史提出过程。

- 检验记录 T1 的首要业务身份固定为 **样品名称、样品编号、物料批号**，优先于任务号、类型和状态。样品名称必须来自 `qms_sample` 对应检验对象/样品来源的受控业务映射；现有表无独立 `sample_name` 列时，标准来料样由 `material_lot_id` 关联检验对象名称派生，`OTHER_APPROVED` 使用已批准 `other_sample_name`。不得把 `materialName` 仅换成“样品名称”标签冒充新事实。
- 检验员先用样品名称/编号/批号定位，再按任务状态、检验人和检验单类型选择本人待检/待复核任务。请验日期和取样日期用于判断时效，必须在列表可见。
- 用户业务口径中的 **检验单号就是检验报告号**，来源 `qms_inspection_report.report_no`；`qms_inspection_task.inspection_task_no` 仅称检验任务号。报告未生成时检验任务不得伪造检验单号。
- 检验任务原始综合判定保持待判定/合格/不合格。让步接收属于后续有调查和 QA 授权的受控质量处置；在决定前显示“不合格（待 QA 处置）”，不得覆盖原始 FAIL。
- 当前正式检验任务列表 API 尚未证明提供上述跨表只读投影与组合查询，后续 G3 必须形成有界 DTO/查询设计并走批准；本节只授权 G1 产品稿和受控规格修订，不授权修改正式 API、DB、权限或状态机。

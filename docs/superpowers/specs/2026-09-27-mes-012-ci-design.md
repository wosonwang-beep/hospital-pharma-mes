# MES-012 Continuous Integration Design

## 1. Purpose

MES-012 adds reproducible continuous integration to the public Hospital Pharmaceutical MES repository. Every pull request and every push to `main` must automatically validate the backend, frontend, infrastructure integrations, and repository contracts before later IAM/RBAC or production work begins.

The work is limited to continuous integration and the tests required to prove the existing Foundation integrations. It does not add IAM, authorization data, audit persistence, master-data behavior, production business behavior, deployment, artifact publication, or release automation.

## 2. Success Criteria

The public repository exposes one GitHub Actions workflow whose required validation is divided into four independently diagnosable jobs:

1. backend build and tests;
2. frontend tests, type checking, build, and dependency audit;
3. MariaDB, Flyway, MyBatis-Plus, and Redis integration tests;
4. repository and Docker Compose contract checks.

All four jobs must pass for the workflow to pass. A clean GitHub-hosted runner must be able to reproduce the result without repository secrets, proprietary MinIO licensing material, an embedded database, or state left by an earlier run.

## 3. Workflow Architecture

Create `.github/workflows/ci.yml` as the single MES-012 workflow. It runs for:

- every pull request;
- every push to `main`;
- manual dispatch for diagnosis.

Concurrency is grouped by workflow and Git reference. A newer run for the same pull request or branch cancels its obsolete predecessor.

Workflow permissions are read-only. No job receives permission to modify repository contents, publish packages, create releases, or deploy environments.

The workflow pins these runtime lines:

- Java 21;
- Maven 3.9 or newer;
- Node.js 22;
- Ubuntu GitHub-hosted runners.

Dependency caches may contain Maven and npm download caches only. Build output and application data are not restored across runs.

## 4. Job Boundaries

### 4.1 Backend

The backend job checks out the repository, installs Java 21 with Maven dependency caching, and runs the complete Maven reactor test suite. Maven Enforcer remains responsible for the Java floor, Maven floor, dependency convergence, and upper-bound dependency rules already defined in the root build.

The job must not require MariaDB or Redis. Tests that require real infrastructure are selected by the integration job instead.

### 4.2 Frontend

The frontend job installs Node.js 22 with npm caching and runs, in order:

1. `npm ci`;
2. the non-watch Vitest suite;
3. TypeScript checking;
4. the Vite production build;
5. a production dependency audit that fails on high or critical vulnerabilities.

The lock file is authoritative. CI must not rewrite it.

### 4.3 Infrastructure Integration

The integration job starts ephemeral MariaDB and Redis service containers with temporary, workflow-local credentials. It waits for their health checks before starting Maven tests.

Spring Boot uses an explicit `ci` profile. The profile reads connection values from environment variables and contains no durable credentials. It must not fall back to H2, an in-memory Redis substitute, or mocks when a required service is unavailable.

Integration coverage proves:

- Flyway migrates an empty MariaDB database successfully;
- the Foundation verification table exists after migration;
- MyBatis-Plus performs a real insert and query against MariaDB;
- the database test rolls back or otherwise removes its test data;
- Redis performs a namespaced write, read, and cleanup against the real service.

Infrastructure startup, connectivity, migration, or assertion failures fail the job directly.

### 4.4 Repository Contract

The repository-contract job verifies the existing Compose topology and repository hygiene without starting licensed MinIO AIStor. It checks the committed Compose definition, required project directories, and absence of tracked build output or local secret files.

MinIO/AIStor remains a configuration boundary in CI. The workflow must not commit, request, or expose an AIStor license. Runtime validation of the licensed service remains a documented local or controlled-environment responsibility.

## 5. Test Organization

Infrastructure tests must be distinguishable from the normal unit and application-context suite so the backend job remains independent of external services. Maven configuration will provide an explicit integration-test entry point used only by the integration job.

Tests use existing public contracts wherever possible. New test-only helpers must remain inside test source sets and must not introduce production behavior solely to make CI pass.

Test data uses unique or deterministic CI-safe identifiers and is cleaned up. No test may depend on execution order or state created by another test or workflow run.

## 6. Failure Handling and Diagnostics

Each job has a descriptive name, and each command fails the job immediately on a non-zero exit. Logs must identify whether a failure came from compilation, unit tests, type checking, production build, dependency audit, service health, Flyway migration, database access, Redis access, or repository policy.

Credentials, tokens, connection strings containing passwords, and service payloads that could contain secrets must not be deliberately printed. GitHub masks are not a substitute for avoiding sensitive output.

Test reports may be uploaded when a failure occurs. Any diagnostic artifact uses a short retention period and contains no credentials or database dumps. Frontend build output is verified, not published as a release artifact.

## 7. Documentation and Repository Policy

The root README will display the CI status for `main` and explain the distinction between local verification and GitHub integration verification.

`AGENTS.md` will record that changes must pass the applicable CI jobs before merge. This is an engineering rule; configuring a GitHub branch-protection rule is outside MES-012 because repository administration is separate from the versioned implementation.

Local scripts remain useful and should share underlying commands or conventions with CI where practical. CI configuration must not silently diverge from the documented local workflow.

## 8. Acceptance Tests

MES-012 is accepted when:

- the workflow syntax is valid and triggers on pull requests, pushes to `main`, and manual dispatch;
- workflow permissions are read-only and concurrency cancellation is configured;
- the backend job passes the full Maven reactor on Java 21;
- the frontend job installs reproducibly, tests, type-checks, builds, and audits production dependencies;
- the integration job proves Flyway, MyBatis-Plus, MariaDB, and Redis against real service containers;
- failure of either service causes the integration job to fail instead of using a substitute;
- the repository-contract job validates Compose and repository hygiene without requiring a MinIO license;
- no real secret, license file, generated dependency directory, or build output is committed;
- README and `AGENTS.md` accurately describe the implemented CI behavior;
- the public GitHub Actions run completes successfully for the implementation branch or pull request.

## 9. Deferred Work

The following remain outside MES-012:

- GitHub branch-protection administration;
- deployment workflows and environments;
- container image building or publication;
- Maven or npm package publication;
- release tagging and changelog automation;
- secret-backed MinIO/AIStor runtime tests;
- scheduled dependency updates;
- static application security testing beyond the defined dependency checks;
- IAM/RBAC and all later MES business epics.
